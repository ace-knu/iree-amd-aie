## 1. 무엇을 재현하는가 (흐름상 위치)
- AIE2P(npu4) 코어의 bf16 행렬곱은 **bfp16 에뮬레이션**이다. 단계는 다음과 같다:
  1. bf16 → `v32accfloat` → `v64accfloat.to.v64bfp16ebs8`(8개 묶음 공유 지수, 가수 8비트)
  2. MAC `@llvm.aie2p.BFP576.BFP576.ACC2048.mac.conf`(conf 780 = sgn_x 1, sgn_y 1, amode 2, bmode 1, zero_acc 0. Peano `mac_8x8_8x8T`와 같음)
  3. MAC 하나 = 8×8 출력 × K 8개(B 전치형). MAC 사이에서 누산기 C는 f32로 메모리에 저장·적재된다.
- 이 흉내는 위 과정의 **NPU 출력을 비트 단위로** 재현한다.
- 적용되는 컴파일 경로(두 경로의 하드웨어 출력은 비트 동일, 확인함):
  - 규민 aievec 하강: `--iree-amdaie-enable-vectorization-passes=true`
  - Peano bfp16 ukernel: `--iree-amdaie-enable-ukernels=matmul --iree-amd-aie-enable-chess-for-ukernel=0`
- 쓰임: 커널 정확도 기준("흉내와 원소 100% 비트 일치"). NPU 실행 없이 기대 출력을 만들 때도 쓴다.

## 2. 입력 → 동작 → 출력
- **입력**: A(M×K), B(K×N) f32(또는 bf16 값), 반올림 모드(`floor` / `half_even` = crRnd floor / conv_even)
- **동작**(규칙):
```
양자화(bfp16ebs8): x → bf16 RNE → K 방향 8개 블록(A는 행 안, B는 열 안)
    e = floor(log2 max|블록|);  q = 반올림_crRnd(x / 2^(e-6));  q ∉ [-128, 127]이 하나라도 있으면 e ← e+1로 다시 양자화
    (1) e < -126 (bf16 비정규만 있는 블록) → 블록 전체 0
누산(K 블록 t = 0, 1, …, 순서대로, 출력 원소마다):
    S   = Σ_{k∈t} qA·qB                                   (블록 안 곱의 합 — 정확)
    E   = max( floor(log2|acc|), eA_t + eB_t )             (acc = 0이면 eA_t + eB_t)
    new = f32_RNE( RNE(acc, 2^(E-23)) + RNE(S, 2^(E-23)) )  (정렬 반올림은 crRnd와 무관하게 RNE)
    (2) new ≠ 0 이고 |new| < 2^-126 → 부호를 유지한 0
    (3) A 블록 또는 B 블록이 전부 0 → acc ← acc + (+0)   (값은 그대로, -0은 +0)
```
- **출력**: M×N f32. 도구는 NPU 출력과 비트 일치율을 보고한다(V3.1 외에 옛 모델 V1·V2와 허용오차 비교도 함께).

## 3. 근거 (확인함)
- **두 경로 비트 동일**: 같은 입력에서 ukernel 경로와 aievec 하강 경로의 출력이 rand·relu, floor·conv_even 모두 같다.
- **오차 위치 가르기**(지정 입력, 256×64×32):
  - 곱 하나(T1)와 블록 안 합(T4)은 정확하다.
  - 작은 블록이 쌓인 누산기에 큰 블록을 더할 때(T2)만 비트를 잃는다(V1 대비 15%).
  - T2 불일치 2,461개 전부에 공통인 규칙이 "누산기를 2^(eA+eB−23) 격자로 RNE"였다. 이것을 일반화해 E = max(acc 지수, eA+eB)로 정했다.
- **기각한 가설 6계열**:
  - A 양자화 변형
  - 누산 순서(24가지)
  - 작은 피연산자 정렬 잘라내기(f32 창)
  - 더 좁은 창
  - MAC 타일(8행·8열) 공유 지수 창
  - 누산기만 블록 지수 창(짝수 W)
- **경계 시험**:
  - 큰 부호 상쇄, 아주 작은 지수(곱 ~1e-31), 블록 안 극단 지수는 V3 그대로 맞는다.
  - 비정규에서 (1)~(3)이 필요하다:
    - bf16 비정규 입력은 곱이 정규여도 0이다.
    - 곱이 f32 비정규이면 0이다. 0의 부호는 마지막 블록 합의 부호와 100% 일치한다.
    - 뒤 블록이 전부 0이면 +0이다.
- **확인한 데이터(모두 비트 일치 100%)**:

| 데이터 | 경우 | 기존 V1(f32 RNE 누산) |
|---|---|---|
| 행렬곱 흉내 입력: 하강 floor·conv_even × 4모양(K 32~2304) × rand·relu | 16 | relu 80.6~99.995% |
| ukernel 경로 floor·conv_even × 2모양 × rand·relu | 8 | relu 80.6~95.6% |
| 지정 입력 T1~T4, 경계 C1·C2·E1~E7 | 13 | 일부 |
| **VGG16 벡터화(conv_even) 실제 dispatch**: conv1_1(K 27), conv4_2·conv5_2(K 4608), fc6(K 25088, N 8조각) | 4 | 58.7~100% |

- VGG dispatch 검증 방법:
  - `--iree-flow-trace-dispatch`(두 단계 컴파일)로 실제 입력과 출력(6자리)을 받았다.
  - 코어 ELF·CDO가 VGG dispatch와 **바이트 동일한 단독 matmul**에 같은 입력을 넣어 이진 출력을 받았다.
  - 그 이진 출력을 흉내와 비교했다. 단독 출력도 VGG 추적과 6자리 100% 같다.
- 입력의 0이 많을수록(ReLU 뒤 깊은 층, A의 0 비율 76~95%) V1은 틀리고 V3.1은 맞는다:

| 층 | A의 0 비율 | V1 비트 일치 |
|---|---|---|
| conv4_2 | 76% | 90.3% |
| conv5_2 | 82% | 89.0% |
| fc6 | 95% | 58.7% |

## 4. 사용법
`tools/bfp16_emulator/README.md` 참고. 함수는 `from bfp_strict_v3 import bfp, bfp_exp, acc_hw`로 import한다(2026-10-22 세션 2에 `__main__` 보호 추가, CLI 동작 같음. 회귀 V1·V2가 이렇게 쓴다). 요약하면 다음과 같다.
- `python3 bfp_strict_v3.py <NPU 출력.npy> <A.npy> <B.npy> <floor|half_even>`
- `V3.1(하드웨어 규칙) 100.0000%`이면 통과다.
- K가 8의 배수가 아니면 0으로 채운다. B가 전치형이면 `.T`를 쓴다.

## 6. 추정인 해석
아래는 관찰과 맞는 **해석**이다. 하드웨어 문서로 확인하지 않았다.
- MAC이 누산기와 블록 합을 **공통 지수 E 아래 23비트 고정소수 창**으로 정렬해 더한다. 블록 쪽 지수는 실제 크기가 아니라 블록 지수 합 eA+eB를 쓴다.
- 블록 지수의 표현 하한이 bf16 정규 하한 근처라서, 비정규만 있는 블록은 0이 된다.
- 결과 FTZ는 부호를 유지한다. 0 블록 MAC은 IEEE식으로 +0을 더한다.
