# BERT-base 두 번째 버그(dispatch-type-transition 비결정론) — 2026-09-04~06 조사 정리

이 문서는 `docs/2026-08-24_int8_quantization_investigation.md` §11-21에 세션 로그
형태로 기록된 내용을 날짜 기준으로 다시 정리한 요약본이다. 상세 근거/명령어/로그는
원본 문서를 참고하고, 여기서는 **지금까지 확정된 사실 / 반증된 가설 / 남은 질문**을
빠르게 파악할 수 있도록 정리한다.

## 배경

- BERT-base를 int8 양자화 + NPU(npu4/Strix) vectorized 경로로 돌리면, **동일한 입력에
  대해 실행마다 다른 출력**이 나오는 버그가 있음(비결정론). 정수 연산이라 결합법칙이
  성립하므로, 이런 경우 매번 비트 단위로 동일한 결과가 나오는 게 정상이다 — 지금
  보이는 현상은 GPU floating-point reduction 순서 차이 같은 "정상적인 미세한 흔들림"이
  아니라, 하드웨어 동기화(race condition)의 전형적인 특징(이산적으로 다른 값, 노이즈성
  요동 아님)이다.
- 첫 번째 버그(batch-0 lock pre-charge race)는 이미 근본 원인 규명 + 커밋된 delay-fix로
  해결됨(`1600078`). 이 문서가 다루는 건 그 이후에도 남아있는 **두 번째 버그** —
  dispatch **타입이 바뀔 때**(예: 비배치 projection matmul ↔ 배치 attention matmul)
  발생하는, delay로 안 고쳐지는 별개의 비결정론.
- 프로젝트 방향: 드라이버/펌웨어 레벨까지는 안 들어가고, **코드/컴파일러 레벨**에서
  원인을 규명하는 것이 목표(ML 입력 → 코드 생성 → Peano 컴파일 → NPU 실행이라는
  파이프라인의 컴파일러 팀 관점).

## 1. IRON(손으로 짠 raw AIE MLIR, `aiecc`)으로 구조를 재현하려는 시도 — 전부 negative

실제 IREE가 만드는 control code 구조를 하나씩 손으로 복제해서 alternation 테스트를
반복함(전부 8컬럼, 매 dispatch마다 실제와 동일하게 fresh `xrt::hw_context` 생성):

1. 단순 toy(다른 프로그램 두 개 번갈아 실행) — negative
2. 진짜 batch 실현 메커니즘 두 가지 다 시도(core-internal 루프, 그리고 실제 IREE가
   쓰는 shim-DMA `repeat_count` 하드웨어 반복) — 둘 다 negative
3. 여러 컬럼의 완료 신호를 하나로 묶는 실제 구조(`amdaie.npu.tct_sync`의
   `col_num=8/8/4`, mlir-aie의 고수준 `dma_wait` API는 이걸 표현 못해서 저수준
   `aiex.npu.sync`를 직접 써야 했음) — negative
4. 실제 matmul 스케일(K=768 리덕션, PDI 크기 54KB까지 키움) — negative

**결론: 소스에서 확인 가능한 구조적 차이는 이 시점에서 사실상 다 닫혔는데도 재현 안 됨.**
IRON은 최대 200번(100라운드)까지 dispatch 교대를 시도했는데, 이건 chainmix(§3)의
최소 재현 크기(L=10, 즉 20번)보다 10배 많은 횟수다 — **"재구성 횟수만으로는
부족하다"는 강한 증거.**

**단, 벡터화(`aievec.matmul`)만은 IRON에서 테스트 못 함** — `aiecc`(mlir-aie 업스트림
독립 툴체인)가 int8 8x8x8 `matmul_aie2p`의 코드 생성을 실제로 지원 안 하는 것으로
보임(4가지 다른 MLIR 구조 전부 `llc`에서 동일한 지점(`G_CONCAT_VECTORS`)에서 크래시,
mlir-aie 자체 lowering 테스트에도 이 조합에 대한 커버리지가 아예 없음). bf16으로도
시도했지만 다른 지점에서 크래시. **이건 "negative 결과"가 아니라 "테스트 자체가
불가능했다"는 뜻** — 원래 첫 번째 버그가 vectorization에서만 나타났던 선례가 있어서,
이 축이 여전히 의심스러운 상태로 남아있었음.

## 2. 실제 IREE 컴파일 vectorized int8 아티팩트 재사용

`aiecc` 대신, **원래 버그#1 조사(8/24) 때 IREE로 컴파일해서 실제 하드웨어에서 검증까지
끝난 진짜 vectorized int8 matmul**(`mm_int8.vmfb` 비배치, `bmm_int8.vmfb` 배치)이
이미 있었음. `iree-run-module`로 직접 15회씩 번갈아 실행(별도 프로세스)했더니 완전히
결정론적이었지만, 이건 L=1급 스케일 + 매번 새 프로세스라 약한 테스트라 정보량 낮음.

## 3. `chainmix_L*` — 실제 BERT가 아니라 구조만 격리한 합성 테스트

`gen_chained_mixed.py`가 만드는 `chainmix_L{N}`은 **BERT를 돌리는 게 아니라**, BERT의
LayerNorm/Softmax/GELU 등 실제 의미는 다 빼고 **"비배치 MatMul → Reshape/Transpose →
배치 MatMul → Transpose/Reshape"** 패턴만 N번(레이어 수만큼) 반복하는, 순수하게
"dispatch 타입 교대 + 타일 재사용"만 격리한 합성 구조다. 이게 실제 IREE 프로덕션
컴파일러로 컴파일되고(벡터화 포함), **오늘도 여전히 재현됨**(15번 재실행 중 12번
동일값, 3번은 각각 다른 값, corr 0.965~0.971).

### D와 HEADS가 뭘 의미하는가

레이어 하나당 구조:
```
[32,D] --비배치 MatMul[D,D]--> [32,D] --reshape/transpose--> [HEADS,32,HD] --배치 MatMul[HD,HD]--> ... --> [32,D]
```
- **D**(원래 768, BERT-base의 hidden size): 비배치 matmul 자체의 크기(K=N=D)를 결정.
- **HEADS**(원래 12, num_attention_heads): 배치 matmul의 **배치 개수(반복 횟수)**를 결정.
- **HD = D/HEADS**(원래 64): head 하나의 배치 matmul 크기.
- D, HEADS, HD는 D=HEADS×HD로 묶여 있어서 **셋 중 둘만 독립적으로 조절 가능** —
  "D는 고정하고 HEADS만 바꾼다"는 건 사실 HD도 같이 바뀐다는 뜻.

### corr가 "거의 100%"처럼 보이는 착시

L=12에서 corr=0.965인 "덜 심각해 보이는" 케이스를 원소 단위로 직접 세어보니, 실제로는
**24576개 중 2728개(11.10%)가 다르고 최대 절대 차이 0.28**이었다(출력값 자체가 보통
0.01~0.15 스케일임을 감안하면 작지 않은 차이). Pearson correlation은 "일부가 상당히
다르지만 나머지 대부분이 일치"하는 상황에 안 민감해서 착시를 일으킨다 — corr 숫자만
보고 "거의 정상"이라고 판단하면 안 된다. 예전 문서의 "0.70-0.90" 기록과 다른 이유는
이 조사 자체가 이미 확인한 "레이스 발생 빈도/심각도가 시간에 따라 통제 안 되는 요인
(온도/부하/드라이버 상태)으로 흔들린다"는 사실로 설명 가능 — 버그가 약해진 게
아니라 표본마다 심각도가 다른 것.

## 4. 최소 재현 L의 재측정 — 임계값이 이동함

같은 스크립트/플래그로 L=6,8,10,12,16을 새로 컴파일해서 각각 20~45회 재실행:

| L | 결과(재현률) |
|---|---|
| 6 | 45/45 결정론적 (재현 안 됨) |
| 8 | 20/20 결정론적 (재현 안 됨) |
| **10** | **재현됨 (20회 중 5회, 2.35% 원소 차이, 2개 값으로만 분리)** |
| **11** | **100/100 결정론적** (재현 안 됨, 2026-09-06 확인 — 20개에서 시작해 100개까지 늘려도 그대로) |
| **12** | **재현됨 (15회 중 4회, 최대 11% 원소 차이, 2개 값으로만 분리)** |
| **13** | **재현됨 — 20회 중 12회가 다름, 무려 6개의 서로 다른 값으로 분리, 최악의 경우 19.89% 원소 차이/최대 절대차 0.4288 (2026-09-06 확인, 지금까지 중 가장 심각)** |
| **14** | 40/40 결정론적 (재현 안 됨, 2026-09-06 확인) |
| **16** | 40/40 결정론적 (재현 안 됨) |

**2026-09-06 업데이트: L=11,13,14를 추가로 확인.** 결과가 예상보다 훨씬
불규칙함(irregular) — 단순 "짝수만" 패턴도 아니고(L=13은 홀수인데 가장 심각), 단순
"L=10~12 좁은 창"도 아님(L=11은 그 사이에 끼어있는데 재현 안 됨). 특히 **L=13은
20회 중 12회가 서로 다른 6개의 값으로 갈렸고, 이 중 하나는 원소의 20%가 다르고
최대 절대 차이 0.43으로 이 조사 전체에서 가장 심각한 케이스**임. 이 정도로
불규칙한 패턴은 "재현에 필요한 최소 크기를 넘으면 그 뒤로는 점점 심해진다"는
단순 임계값 모델보다는, **L(정확히는 총 dispatch 개수/컨트롤 코드 길이)에 따라
어떤 하드웨어 내부 주기(카운터, 타이머, 링버퍼 인덱스 등)와 우연히 맞아떨어지거나
어긋나는 "beat frequency" 성격에 더 가까워 보임.** 다만 표본 수가 L값마다
15~45개로 제한적이라, 재현 안 된 L(6,8,11,14,16)들도 발생률이 매우 낮아서(예:
L=13처럼 60%가 아니라 1~2% 수준) 지금 표본 수로는 못 잡았을 가능성은 완전히
배제 못함 — L=10,12,13이 진짜로 "0%"인 L들과 질적으로 다른지, 아니면 그냥
발생률이 연속적으로 낮아지는 건데 표본이 부족한 건지는 미확정.

예전 문서(같은 파일의 "Thirteenth" 실험)에는 L=6,8에서 이미 이산적 분리가 있었다고
기록돼 있었는데, 오늘은 재현 안 됨 — 8/24 이후 이 컴파일러에 여러 커밋(row-overflow
수정, batch matmul padding 수정, accumulator rescale 수정, batch-0 delay-fix 등)이
반영되면서 소스는 동일해도 실제 생성되는 control-code/타이밍 특성이 달라져 정확한
트리거 조건이 이동한 것으로 추정(직접 diff는 안 함). **버그 자체는 안 고쳐졌음
(L=10,12 오늘도 재현) — 다만 최소 재현 크기가 바뀜.**

**L=16이 재현 안 된다는 게 특히 중요하다** — "레이어가 깊어질수록 스트레스가 쌓여서
점점 더 잘 터진다"는 단순 누적/단조증가 가설과 안 맞는다. L=10,12에서는 재현되고
그보다 얕은(6,8) 것도 깊은(16) 것도 재현 안 되는 건, 어떤 **좁은 범위에서만 우연히
타이밍이 맞아떨어지는 "공진(resonance)"에 가까운 패턴**을 시사한다. 아직 L=14는
확인 안 함(재현 창이 정확히 어디서 닫히는지 미확정).

## 5. D(hidden dim) 축소 시도 — 크기도 독립적인 필요조건

`gen_chained_mixed_mini.py`로 D/HEADS를 파라미터화해서 축소 시도(**L=12로 고정,
이미 재현되던 값**):

- D=64, HEADS=2: 20/20 결정론적, 재현 안 됨. (단, 배치 개수 2가 너무 작아서
  `repeat_count` 하드웨어 반복 메커니즘 자체가 안 쓰이고 완전 unroll로 컴파일됨 —
  원본과 다른 배치 구현이라 순수 크기 비교로는 오염됨)
- D=384, HEADS=6(원래의 절반, HD=64는 원본과 동일 유지): 20/20 결정론적, 재현 안 됨.
  **이건 배치 메커니즘(`repeat_count=6`)까지 원본과 동일하게 유지한 가장 깨끗한
  비교인데도 재현 안 됨.**

### 타일/컬럼 배치 직접 diff (`--mlir-print-ir-after-all`)

- `tct_sync`의 `col_num`(몇 개 컬럼에 걸쳐 완료를 기다리는지): D=768/384/64 전부
  `8/8/4`로 **byte-identical**. → **컬럼 개수 가설 반증** — 컬럼 스프레드는 D 크기와
  무관하게 항상 고정(8개).
- `write_bd`의 `buffer_length`(실제 DMA 전송 바이트): **D에 정비례해서 스케일링됨.**

| | 최대 buffer_length | 배치 메커니즘 | 재현? |
|---|---|---|---|
| D=768 | 18432 bytes | repeat_count=12 | 됨 |
| D=384 | 4608 bytes (정확히 1/4) | repeat_count=6(동일 메커니즘) | 안 됨 |
| D=64 | 512 bytes | repeat_count=1(다른 메커니즘) | 안 됨 |

- bd_id 개수(D=768 첫 dispatch 근처)는 0,1,2 세 종류뿐 — "큰 전송을 여러 BD로
  쪼갠다"기보다는 원래 있던 input/weight/output ping-pong 구조가 재사용되는 것으로
  보임(D=384/64 쪽 bd_id 개수까지는 재확인 안 함 — 미해결 항목).

**결론: "컬럼 개수"가 아니라 "dispatch 하나가 실제로 옮기는 DMA 데이터량(=하드웨어를
점유하는 시간)"이 진짜 변수.** 이건 "호스트 딜레이를 아무리 넣어도 안 고쳐졌다"는
기존 사실(Seventeenth/Eighteenth 실험)과도 정합적 — 문제는 "경과 시간"이 아니라 "그
dispatch 자체가 실제로 하드웨어를 점유하는 시간/데이터량"이라는 뜻.

## 현재까지의 종합 결론

버그는 **최소 두 개의 독립된 임계값 조건을 동시에 만족해야 재현**되는 것으로 보인다:

1. **충분한 dispatch 교대 횟수(L)** — 단, 단조증가가 아니라 **L=10~12 근처의 좁은
   구간에서만** 재현되고 L=16처럼 더 깊어지면 오히려 사라짐(공진 패턴 가능성).
2. **충분한 dispatch당 DMA 전송량(D)** — D=768 필요, 절반(D=384)만 돼도 사라짐.
   컬럼 개수는 무관함이 확인됨(반증).

두 조건 중 어느 하나만 충족해도 재현 안 됨:
- IRON(§1)에서 횟수만 200번까지 쌓아도(D는 사실상 작은 toy 스케일) 재현 안 됨.
- D=768(§5, L=12 고정)에서도 크기를 줄이면 재현 안 됨.

## 아직 안 풀린 질문 / 다음 후보

- **L에 따른 패턴이 예상보다 훨씬 불규칙함(2026-09-06, L=11,13 확인 후)** — "짝수만"
  가설도, "L=10~12 좁은 창" 가설도 둘 다 깨짐(L=11은 그 사이에서 재현 안 되고, L=13은
  가장 심각).
- **L=11을 100개 표본까지 늘려서 재확인함(2026-09-06) — 100/100 결정론적, 그대로
  재현 안 됨.** 즉 L=11은 표본 부족으로 놓친 게 아니라 진짜로 깨끗하거나(또는
  L=10,12,13보다 발생률이 현저히 낮음)로 봐도 될 만큼 확인됨. **"L=10~13 구간
  전체가 위험한데 발생률만 들쭉날쭉"이 아니라, L=11은 질적으로 다른 안전 지점일
  가능성이 더 높아짐.**
- 다른 "재현 안 됨" L(6,8,14,16)도 L=11처럼 표본을 100개까지 늘려서 같은 수준으로
  확인이 필요한지는 미정 — 지금 우선순위는 L=15,17~20 등 아직 안 본 구간을 넓히는
  쪽이 더 급함(L=13 이후 다시 사라지는지, 산발적으로 더 나오는지 확인).

### 정적 구조 분석으로 "왜 하필 L=10,12,13인지" 규명 시도 — 전부 negative

**dispatch/instruction 개수**: push_to_queue/write_bd/address_patch/tct_sync
개수를 L=10~14에서 직접 세어보니 레이어당 정확히 40/40/40/6개씩 완벽하게 선형으로
증가(L=10→400, 11→440, 12→480, 13→520, 14→560). L=10,12,13에서만 특별한 배수나
경계를 지나는 지점 없음.

**타일/컬럼 배치**: `--mlir-print-ir-after=iree-amdaie-controlcode-lowering`로
L=10,11,12,13,14 전부의 "레이어 0" dispatch(비배치)가 사용하는 `col = X` 시퀀스를
직접 비교 — **바이트 단위로 완전히 동일**(`7,7,7,6,6,6,...,0,0,0` 패턴이 L값과
무관하게 그대로). **즉 타일/컬럼 배치는 총 레이어 수(L)를 컴파일러가 알고
계산하는 게 아니라 dispatch 구조 자체에 고정된 값 — "특정 L에서 우연히 나쁜
타일에 배치된다"는 가설은 이걸로 반증됨.**

**결론: 정적 구조(개수, 크기, 배치)로 설명 가능한 후보는 이 시점에서 사실상 다
소진됨.** 남은 건 실행 시점의 정확한 타이밍(하드웨어가 그 순간 정확히 뭘 하고
있었는지)뿐인데, 이건 정적 분석으로는 원천적으로 안 보이는 영역 — 지금까지
이 조사에서 소스/IR 레벨로 확인한 모든 다른 층(락, BD, DMA queue-drain,
wait-fold, TCT-sync lowering)이 전부 깨끗했던 것과 같은 패턴.
- **HEADS를 D는 고정한 채 독립적으로 바꾸는 실험 안 함** — D=768 유지, HEADS=6(HD=128,
  repeat_count=6)처럼 비배치 matmul 크기는 그대로 두고 배치 쪽 구조만 바꿔보는 실험이
  필요. D=HEADS×HD로 묶여있어서 완전한 독립변수는 아니지만, 이 조합은 아직 안 해봄.
- **D=384/64의 bd_id 개수(BD가 여러 개로 쪼개지는지) 미확인** — "DMA 채널을 더 많이
  써서 아비터 경합이 생기는지" 가설을 완전히 검증하려면 필요.
- **중간 D 값(512, 640 등) 스캔 안 함** — D=384(절반)에서 이미 실패한 걸 보면 임계값이
  768에 상당히 가까울 가능성.
- 드라이버/펌웨어 레벨 트레이싱(JTAG/AIE trace unit 등)은 프로젝트 방향상 범위 밖으로
  결정됨 — 코드/컴파일러 레벨에서 계속 파는 것으로 합의됨.
