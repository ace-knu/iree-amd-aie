# 2026-09-10 — BERT e2e를 int8 벡터 연산으로 실행 (65069ce)

## 0. 요약

lock 수정(`65069ce`) 상태에서 BERT를 **int8 양자화 + 벡터화(`aievec.matmul`)** 경로로
e2e 실행했다. 과거 e2e는 bf16 스칼라였다.

- **비결정론이 완전히 사라졌다** — 12층 전체를 10회 돌려 출력 **1종**.
  이 조사의 출발점("L=12에서 실행마다 결과가 달라진다")이 해소됐다.
- **정확도 손실은 NPU 탓이 아니다** — 양자화 모델을 CPU(onnxruntime)에서만 돌려도
  torch 대비 corr 0.884 이고, NPU 는 0.902 로 오히려 더 가깝다(§6).
  손실의 지배 요인은 **캘리브레이션 없이 만든 QDQ** 이고, 컴파일러 작업이 아니다.
- NPU 와 CPU 기준의 f32 발산(~1e-06)이 `QuantizeLinear` 반올림 tie 를 넘겨
  int8 1 LSB 가 틀어지고 attention 의 `QK^T` 가 그것을 전체로 번지게 한다(§5).
  원리상 불가피하지만, 모델이 knife-edge 인 탓에 커 보이는 것이다.

## 1. 방법

- 모델: `_local/int8_debug/out/bert_base{,_L1,_L2,_L4}_int8.mlir`, `bert_tiny_int8.mlir`
  (`main_graph([1,32] si64) -> [1,32,768] f32`)
- 입력: `models/bert_base/input_ids.npy`
- 기준 ①: 같은 양자화 ONNX를 onnxruntime CPU로 실행 → NPU가 *같은 그래프*를 맞게 계산하는지
- 기준 ②: `models/bert_base/ref_last_hidden_state.npy` (torch) → 과거 bf16 값과 직접 비교
- 각 10회, `scripts/lock/with-npu-lock.sh` 로 감쌈

## 2. 결과 — 기준 ① (같은 양자화 그래프, ORT/CPU)

| 모델 | 층 | hidden | corr | maxerr | 출력 종류 |
|---|---|---|---|---|---|
| `bert_tiny` | 2 | 128 | **1.000000** | 1.19e-06 | 1 |
| `bert_base_L1` | 1 | 768 | **1.000000** | 3.34e-06 | 1 |
| `bert_base_L2` | 2 | 768 | 0.997381 | 0.818 | 1 |
| `bert_base_L4` | 4 | 768 | 0.983676 | 0.657 | 1 |
| `bert_base` | 12 | 768 | 0.945584 | 1.856 | 1 |

`bert_tiny`와 `bert_base_L1`의 오차(1e-06 수준)는 f32 ULP 노이즈다. 사실상 정확.

## 3. 결과 — 기준 ② (torch, 과거 bf16 스칼라와 같은 잣대)

| 경로 | corr(torch) | maxdiff |
|---|---|---|
| bf16 스칼라 (2026-08-20) | **0.99998** | ~0.04 |
| int8 벡터 (오늘) | 0.901986 | 2.972 |

## 4. 읽는 법

**해결된 것**: 12층 10회 출력 1종. `chainmix` 계열 27개 모델 320회에서도 실행간 편차 0
(`docs/2026-09-10_verification_campaign_after_lock_fix.md`). 비결정론은 끝났다.

**새로 보이는 것**: 레이어당 일정한 오차가 들어가 누적되는 형태다(L1 0 → L2 → L4 → L12 단조).
`bert_base_L2` 를 진단한 결과:

```
다른 원소 23612/24576 (96.08%)   maxdiff=0.81839  (ref|max|=11.11 → 상대 ~7%)
행별 불일치: 32행 전부 (거의 768/768)
열별: 0인 열 0/768, 평균 30.74
col%8 분포: [2950, 2960, 2942, 2957, 2950, 2953, 2939, 2961]   ← 균등
```

**넓고 균일하게 확산** — lock/DMA 손상의 국소·구조적 서명이 아니다
(lane 버그라면 `col%8==0`에 몰리고, DMA 문제라면 연속 열 구간/슬라이스 블록 단위).
`chainmix_L12_H12`(D=768, HEADS=12, 24 디스패치)는 `maxerr 0` 이었는데 거기엔
LayerNorm·Softmax·GELU가 없다. 즉 차이는 **BERT에만 있는 부분**에서 온다:

1. CPU측 LayerNorm / GELU / Softmax 와의 접합부
2. int8로 양자화되지 않은 matmul의 **bf16 demotion**
3. 양자화 스케일 자체 (캘리브레이션 없이 만든 QDQ)

## 5. 원인 규명 완료 — 컴파일러/하드웨어 결함이 아니다

tap 을 붙여 레이어 경계별로 계측했다. **통제 검증**: tap 넣은 빌드의 최종 출력이
tap 없는 빌드와 **비트 동일**(maxdiff=0)이므로 tap 이 계산을 교란하지 않았다.

### 5.1 오차가 처음 생기는 지점

| 지점 | maxerr | 판정 |
|---|---|---|
| 임베딩 직후 | 1.43e-06 | 정확 |
| layer 0 attention 후 | 1.53e-05 | 정확 |
| **layer 0 경계** | **3.34e-06** | **정확 — layer 0 전체가 맞다** |
| layer 1 attention 후 | 0.0943 | ← 여기서 발생 |
| 최종 | 0.8184 | 누적 |

layer 0 경계값 3.338e-06 은 `bert_base_L1` 의 최종값 3.338e-06 과 정확히 일치한다(교차 검증).
즉 **layer 1 은 올바른 입력을 받아 틀린 출력을 낸다.**

### 5.2 layer 1 내부 — 첫 matmul의 오차는 행 하나에만 있다

| 지점 | shape | maxerr | 상대오차 |
|---|---|---|---|
| L1 query MatMul (비배치) | (1,32,768) | 0.00988 | 0.17% |
| L1 key MatMul | (1,32,768) | 0.01069 | 0.18% |
| L1 value MatMul | (1,32,768) | 0.00837 | 0.29% |
| L1 QK^T (배치 matmul) | (1,12,32,32) | 0.4241 | 0.39% |
| L1 softmax@V (배치 matmul) | (1,12,32,64) | 0.0368 | 1.85% |
| L1 attn dense | (1,32,768) | 0.0342 | 1.75% |
| 최종 | (1,32,768) | 0.8184 | 7.36% |

**L1 query MatMul 의 행별 maxerr**: 행9 = 0.00988, **나머지 31행 전부 ~2e-06**(ULP 노이즈).
4000배 격차로 **행 9 하나에만** 오차가 있다.

### 5.3 원인: QuantizeLinear 경계의 반올림 tie 하나

layer 1 의 QKV matmul 입력은 layer 0 출력을 `QuantizeLinear`(scale 0.07674842, zp 0) 한 것이다.
NPU 가 낸 f32 값과 ORT 의 f32 값을 각각 int8 로 양자화해 비교했다(하드웨어 불필요):

| 지점 | f32 차이 | 1 LSB 대비 | **int8 로 바꾼 뒤 다른 원소** |
|---|---|---|---|
| layer 0 QKV 입력 (scale 0.07987) | 1.43e-06 | 0.0018% | **0 / 24576** |
| layer 1 QKV 입력 (scale 0.07675) | 3.34e-06 | 0.0043% | **1 / 24576** (크기 1, 위치 `[0,9,731]`) |

**딱 한 원소가 반올림 경계에 걸려 int8 값이 1 틀어졌다.** layer 0 은 어느 원소도
경계에 걸리지 않았으므로 정확했다. 이것이 "layer 0 은 맞고 layer 1 은 틀린" 이유 전부다.

### 5.4 증폭 경로

```
f32 3.3e-06 차이 (CPU측 LayerNorm 구현 차이)
  → int8 1 LSB flip, 행 9 · 차원 731  (1/24576 원소)
  → L1 Q/K/V matmul: 행 9 만 틀림 (0.0099)
  → QK^T: K 의 행 9 가 모든 쿼리 행의 열 9 가 됨  ⇒ 32행 전부 오염 (0.42)
  → softmax 가 행 내 32 키에 퍼뜨림
  → @V, attn dense: 768 차원 전체로 섞임
  → 최종 7.36%
```

### 5.5 최종 증명 — 하류는 전부 정확하다

NPU 가 실제로 낸 layer 0 출력을 `onnx.utils.extract_model` 로 뽑은 CPU 하류 그래프에 넣었다.

| 비교 | maxerr |
|---|---|
| NPU 의 layer0 출력 → CPU 하류 결과 **vs NPU 최종** | **3.8e-06** |
| CPU 전체 실행 vs NPU 최종 | 0.8184 |

**최종 오차의 100% 가 layer 0 출력의 f32 3.3e-06 차이 하나로 설명된다.**
NPU 가 그 아래로 계산하는 것은 전부 정확하다.

## 6. 양자화 자체의 손실을 분리 측정 — NPU 는 정확도를 깎지 않는다

torch 를 진짜 정답으로 두고 12층 BERT-base 를 세 갈래로 비교했다.

| 비교 | corr | maxdiff |
|---|---|---|
| torch vs **ORT-int8 (CPU 만)** | **0.883656** | 3.468 |
| torch vs **NPU-int8** | **0.901986** | 2.972 |
| ORT-int8 vs NPU-int8 | 0.945584 | 1.856 |
| (참고) torch vs bf16 스칼라 (2026-08-20) | 0.99998 | ~0.04 |

**양자화 모델을 CPU 에서만 돌려도 이미 corr 0.884 다.** NPU 는 0.902 로 오히려 우연히
torch 에 더 가깝다. 즉 **NPU 경로가 정확도를 깎아먹는 것이 아니고**, 손실의 대부분은
양자화 자체에서 온다. §2 의 "레이어 수에 따른 단조 하락"도 NPU 탓이 아니라
양자화된 모델이 원래 그런 것이다.

## 7. 결론

**설계대로 동작한다.**

- **NPU 의 int8 벡터 matmul 은 정확하다.** `chainmix` 27개 모델 320회 `maxerr 0`,
  BERT 에서도 layer 0 출력을 주면 하류가 3.8e-06 안에서 맞는다(§5.5).
- **CPU 측(양자화 안 된 연산)도 정상이다.** llvm-cpu 와 onnxruntime 이 f32 수준
  ~1e-06 에서 갈리는 것뿐이고, 서로 다른 f32 구현이 비트 일치할 수는 없다.
- **비결정론은 완전히 해소됐다** (12층 10회 출력 1종).

**남은 정확도 격차는 두 갈래이고, 성격이 다르다.**

1. **양자화 자체의 손실 (corr 0.884, 지배적) — 고칠 수 있다.**
   캘리브레이션 없이 만든 QDQ 라 스케일이 최적이 아니다. 대응책:
   대표 입력으로 캘리브레이션, per-channel 스케일(현재는 텐서당 1개),
   민감 레이어만 bf16 로 남기는 혼합 정밀도. **컴파일러 작업이 아니라 양자화 품질 작업.**
2. **NPU vs CPU 기준의 f32 발산 (0.9456) — 원리상 불가피하지만 작다.**
   양자화 안 된 연산의 f32 차이(~1e-06)가 `QuantizeLinear` 의 반올림 tie 를 넘기면
   int8 이 1 틀어지고, attention 의 `QK^T` 가 그 한 행을 전체로 번지게 한다(§5.4).
   1 이 knife-edge 인 탓에 보이는 것이므로, 1 을 고치면 이것도 함께 줄어든다.

**bf16 스칼라의 0.99998 과 직접 비교하는 것은 부적절하다** — 그쪽은 양자화를 하지 않은
다른 수치 체계다. 비교하려면 "캘리브레이션한 int8" 을 만들어야 한다.

⚠️ tap 을 만들 때 **f32 텐서만** 쓸 것 (int8 텐서를 그래프 출력으로 노출하면
`amdxdna/buffer.cc:247` assertion 으로 죽는다 — 별건 버그).
도구: `_local/int8_debug/tools/{add_bert_taps.py,add_bert_taps2.py,extract_from_l0.py}`.
ONNX 임포터는 컨테이너에서
`PYTHONPATH=/workspace/build/compiler/bindings/python python3 -m iree.compiler.tools.import_onnx`.
