# 배치 int8 matmul의 결정론적 레인(lane) 버그 — 2026-09-09

`docs/2026-09-09_core_store_vs_dma_read_race_at_vector_store_granularity.md`의 조사 중
"이게 `proj2`에서만 일어나는 거냐"는 사용자 질문에서 출발해 **24개 NPU dispatch를 전수
검사**한 결과, 지금까지 쫓던 경합과는 **성격이 완전히 다른 두 번째 문제**를 찾았다.

## 0. 먼저 명확히 — 이건 BERT가 아니다

`chainmix_L12`는 **합성 테스트 모델**이다(`gen_chained_mixed.py` 주석에 명시).
LayerNorm/Softmax/GELU 등 실제 attention 의미는 전부 빼고, BERT가 만드는 **dispatch 타입
교대 패턴만** 남겼다. 레이어 1개 = **matmul 2개**뿐이다:

```
[32,768] --비배치 MatMul [768,768]--> reshape [32,12,64] --transpose--> [12,32,64]
   --배치 MatMul [12,64,64]--> [12,32,64] --transpose/reshape--> [32,768]
```

실제 BERT 레이어는 비배치 4개(Q,K,V,output) + FFN 2개 + 배치 2개(QK^T, Attn@V)이므로
크게 축약된 캐리커처다. `D=768`, `HEADS=12`, `HD=64`만 BERT-base 크기를 따랐다.

용어 주의: 앞선 문서들의 "**레이어 2**"는 체인 길이 L=2가 아니라 **12개 레이어 중 인덱스 2
(3번째)** 를 뜻한다.

## 1. 계측 방법 — per-stage residual

전파된 오차 때문에 "어디서 새로 손상되는지"가 안 보이는 문제를 이렇게 해결했다:

**각 단계마다 NPU가 *실제로 받은* 입력을 CPU에 똑같이 넣고, 그 단계의 출력만 비교한다.**
`onnx.utils.extract_model`로 단계별 부분 그래프를 뽑아 쓴다. 그리고 실행간 **편차(spread)** 로
경합과 계통 오차를 가른다:

- 편차 = 0 → 매번 같음 → **계통(결정론적)**
- 편차 > 0 → 실행마다 다름 → **경합**

계측용 tap은 **f32 텐서만** 쓴다(int8 텐서를 그래프 출력으로 노출하면
`runtime/src/iree-amd-aie/driver/amdxdna/buffer.cc:247` assertion으로 죽는다 — 별건 버그).

## 2. 24개 dispatch 전수 결과

### 비배치 matmul (`proj0`~`proj11`) — 정상일 때 비트 수준 정확

| 단계 | 오차 최소 | 오차 최대 | 실행간 편차 | 판정 |
|---|---|---|---|---|
| proj0, 1, 3, 4, 5, 6, 7, 9, 10, 11 | 0 ~ 1.2e-07 | 동일 | **0** | 정확 |
| **proj2** | 0.1677 | **3532** | **3532** | **경합(심각)** |
| **proj8** | 5.96e-08 | **0.6326** | **0.6326** | **경합(작음)** |

### 배치 matmul (`bmm0`~`bmm11`) — 12개 **전부** 틀림

| 단계 | 오차 최소 | 오차 최대 | 실행간 편차 | 판정 |
|---|---|---|---|---|
| bmm0, 1, 3, 5, 6, 7 | 0.1235 ~ 0.3421 | 동일 | **0** | **계통 오차** |
| bmm2, 4, 8, 9, 10, 11 | 0.195 ~ 0.3712 | 0.2128 ~ 0.4521 | 0.0024 ~ 0.081 | 계통 + 작은 경합 |

**즉 24개 중 12개(배치 전부)는 항상 틀리고, 8개는 실행마다 달라진다.**
최종 출력의 corr(0.97)만 보고 있었기 때문에 배치 쪽 계통 오차는 **전혀 안 보였다** —
하류 int8 재양자화 포화가 다 가렸다.

## 3. 계통 오차는 실재한다 — NPU가 틀렸다

비교 기준이 공정한지 확인하기 위해, layer 0의 배치 matmul을 **numpy로 정확히** 계산했다
(int8 → int32 정확 누산 → `× (s_a·s_w)`; `s_a`=0.00297055, `s_w`=0.00356603):

| | 텐서 `|max|` | exact numpy와의 차이 |
|---|---|---|
| **exact numpy int8** (기준) | 0.2741 | 0 |
| **onnxruntime** | 0.2741 | **1.0e-08** ✅ |
| **NPU** | 0.2741 | **0.1235** ❌ |

**onnxruntime이 맞고 NPU가 틀린다.** 계측 방법 문제가 아니다.

## 4. 손상의 정확한 규칙 — 8×8 타일 내부의 레인 패턴

`bmm0`(shape `[12,32,64]` = head 12 × M 32 × N 64) 기준, 손상 원소 128개:

```
head  8, row%8 = 0        -> 32 elems
head 10, row%8 = 2        -> 32
head 10, row%8 = 4        -> 32
head 10, row%8 = 6        -> 32
col%8 분포: {0: 128}      ← 128개 전부 col%8 == 0
```

8×8 출력 타일 좌표로 다시 쓰면:

| head | 타일 내부에서 틀린 (row, col) | 개수 |
|---|---|---|
| **8** | (0, 0) — 타일의 첫 원소 | 4 row-tile × 8 col-tile = 32 |
| **10** | (2, 0), (4, 0), (6, 0) | 4 × 8 × 3 = 96 |

- **128개 전부 `col % 8 == 0`** — 8칸 그룹의 **첫 번째 레인**
- 해당 head의 **모든 타일에서 같은 레인**이 틀린다
- 값은 절반가량이 **정확히 0**(NPU 출력의 exact-zero 68개 vs 기준 4개), 나머지는 다른 틀린 값
- 예: head 8, row 0의 손상 열 `{0,8,...,56}`에서 NPU는 전부 `0.0`, 기준값은
  `0.0667 / -0.0518 / 0.0358 / 0.0559 / 0.0856 / 0.0833 / -0.1235 / -0.0028`

### 값·레이어·입력에 완전히 무관하다 — 순수 구조적 버그로 확정

세 층위에서 모두 동일함을 확인했다:

1. **실행 간**: 매 실행 손상 마스크가 비트 단위로 동일.
2. **레이어 간**: 12개 레이어 전부 동일한 좌표. 레이어별 가중치(`w1_k`)와 스케일이
   전부 다른데도 같다 ⇒ 가중치·스케일 무관.
3. **인스턴스 간**: 별도 입력·별도 스케일로 만든 clean 인스턴스(`L12_s0`,
   경합은 전혀 없는 것)에서도 **한 글자도 다르지 않다**:

```
layer  #diff  rule (head, row%8) -> count                                   col%8
    0    128  h8/r%8=0:32, h10/r%8=2:32, h10/r%8=4:32, h10/r%8=6:32      {0: 128}
    1    128  h8/r%8=0:32, h10/r%8=2:32, h10/r%8=4:32, h10/r%8=6:32      {0: 128}
    5    128  h8/r%8=0:32, h10/r%8=2:32, h10/r%8=4:32, h10/r%8=6:32      {0: 128}
   11    128  h8/r%8=0:32, h10/r%8=2:32, h10/r%8=4:32, h10/r%8=6:32      {0: 128}
```

⇒ **값에 전혀 의존하지 않는 순수 구조적(코드 생성) 버그.** §2의 경합(값·타이밍 의존,
인스턴스마다 다름)과 성격이 정반대다.

이것은 앞선 조사에서 "clean"으로 분류했던 인스턴스들에 대한 해석도 정정한다: 그것들은
**경합이 없었을 뿐이고, 배치 matmul은 거기서도 똑같이 틀리고 있었다.**

## 4-b. 최소 재현체 확보 + head 수 스윕 — 버그는 head 8부터 시작한다

### 최소 재현체

chainmix의 배치 matmul과 **정확히 같은 형태**(`[HEADS,32,HD] @ [HEADS,HD,HD]`)의 단독
int8 배치 matmul을 만들었다: `_local/int8_debug/gen_bmm_lane_repro.py [HEADS] [M] [HD] [SEED]`.

- **vmfb 156KB, dispatch 1개** (chainmix는 11MB, 24개)
- 4/4 실행 완전 동일, **chainmix와 정확히 같은 규칙 재현**:

```
col%8 = {0: 122}                                  ← 전부 첫 레인
h8/r%8=0, h10/r%8=2, h10/r%8=4, h10/r%8=6         ← chainmix와 동일한 head/행
```

(chainmix에서 128개였던 것이 122개인 건 정답이 0에 가까운 원소 몇 개가 임계값에 안 걸린
것뿐 — 패턴은 동일하다.)

⇒ **이제 dispatch 1개 규모에서 파라미터를 바꿔가며 반복 실험할 수 있다.**

### HEADS 스윕 — 8 이하는 정상, 초과하면 발생

M=32, HD=64 고정, HEADS만 변경:

| HEADS | 손상 원소 | 손상 위치 |
|---|---|---|
| **4** | **0** | 없음 — 완전 정확 |
| **8** | **0** | 없음 — 완전 정확 |
| **12** | 122 | h8/r%8=0, h10/r%8=2,4,6 (열 전부 %8==0) |
| **16** | 938 | h8/h10 위와 동일 **+ h13은 모든 행**, 열도 %8 ∈ {0,1,2,3}로 확산 |

세밀하게 좁힌 전체 스윕 (M=32, HD=64 고정):

| HEADS | 손상 원소 | 손상된 head |
|---|---|---|
| 4 | **0** | — |
| 8 | **0** | — |
| **9** | **0** | — |
| **10** | 31 | **h8** (r%8=0) |
| **11** | 31 | **h8** (r%8=0) |
| **12** | 122 | h8 (r%8=0), **h10** (r%8=2,4,6) |
| **16** | 938 | h8, h10 위와 동일 + **h13은 모든 행**, 열도 %8 ∈ {0,1,2,3} |

관찰:

1. **HEADS ≤ 9면 버그가 없다.** 경계는 9와 10 사이다.
2. **손상되는 head 인덱스가 HEADS와 함께 움직인다**: HEADS=10,11 → h8 하나.
   HEADS=12 → h8 + h10. 즉 **첫 손상 head ≈ HEADS − 2**이고, HEADS가 커지면 손상 head가
   늘어난다 ⇒ **마지막 몇 개 head의 처리 방식**을 지목한다(고정된 절대 인덱스가 아니다).
3. HEADS=10,11에서 h8이 **정확히 같은 31개**(r%8=0, col%8=0)로 손상된다 — HEADS가 달라도
   같은 레인.
4. HEADS=16에서는 h13이 **모든 행**에서 틀리고 열도 `%8 ∈ {0,1,2,3}`로 번진다 ⇒ HEADS가
   커지면 손상 범위 자체도 커진다.

### BD 접근 패턴 스윕 — size 필드 한계는 원인이 아니다

같은 스윕에서 제어 코드의 `write_bd` 파라미터:

| HEADS | 입력 BD | 출력 BD | 세 번째 BD |
|---|---|---|---|
| 4 | `sizes=[0,256,2] strides=[0,16,1]` | `[0,128,8] / [0,64,1]` | `[2,8,8] / [8,16,1]` |
| 8 | `[0,512,2]` | `[0,256,8]` | `[2,8,8]` |
| 12 | `[0,768,2]` | `[0,384,8]` | `[2,8,8]` |
| 16 | **`[16,64,2] strides=[1024,16,1]`** | `[0,512,8]` | `[2,8,8]` |

- 입력 BD의 중간 크기는 `HEADS×64`로 비례하다가, HEADS=16에서 1024가 되어야 할 것이
  **`[16,64,2]`로 3D 분할**된다 ⇒ size 필드는 **10비트(최대 1023)** 이고 컴파일러가 그 한계를
  **올바르게 인식해 분할한다.**
- 8(512)과 12(768) 모두 한계 안에 들어가므로 **필드 오버플로는 원인이 아니다.**
- 세 번째 BD(`len=128, sizes=[2,8,8]`)는 **모든 HEADS에서 완전히 동일**하다.

### AIE 하드웨어 구조는 HEADS와 무관하다

`lower-to-aie` 출력에서 **타일·lock·버퍼·flow·DMA BD 구조 2608줄이 HEADS=8과 12에서
바이트 단위로 동일**하다(차이는 global memref의 batch 차원 숫자뿐). aievec 레벨도 네 경우 모두
동일하다(코어당 출력 타일 `memref<1x1x1x1x1x8x8xi32>` = 8×8 하나, `aievec.matmul` 1개).

⇒ **batch 차원은 device 구조가 아니라 제어 코드의 `repeat_count`(= HEADS)와 BD 접근 패턴
으로만 표현된다.** 따라서 원인은 그 반복/접근 패턴이 마지막 head들을 다루는 방식에 있다.

**"8"이라는 경계가 결정적 단서다.** 8은 이 경로 전체에 걸쳐 반복되는 숫자다 — AIE 컬럼 수 8,
`aievec.matmul`의 8x8x8 타일, 8칸 벡터 그룹(`col%8==0`), 그리고 배치가 코어당 6타일씩
처리되는 구조. HEADS>8에서 batch 차원이 하드웨어 자원(컬럼/채널/BD) 한계를 넘어 접히거나
재사용되는 지점을 의심할 근거가 된다.

## 4-c. HEADS=9 vs 10 IR 비교 + M 통제 실험

### 컴파일러 IR에는 9와 10을 구별하는 구조적 차이가 없다

경계가 9(정상)/10(손상) 사이이므로 그 둘의 IR을 여러 단계에서 비교했다:

| 비교 단계 | 결과 |
|---|---|
| `lower-to-aie` 구조(타일·lock·버퍼·flow·DMA BD) 2608줄 | **바이트 단위 동일** (HEADS=8 vs 12에서도) |
| aievec (`aievec.matmul` 개수, 코어당 출력 타일) | 동일 — `memref<1x1x1x1x1x8x8xi32>` 1개, matmul 1개 |
| `dma-composition`의 `npu.dma_cpy_nd` | **구조 동일**, 숫자만 HEADS에 비례 |
| `npu.circular_dma_cpy_nd` 형태별 개수 | **완전 동일** (32/12/8/8/4) |
| 제어 코드 `write_bd`/`push_to_queue` | 구조 동일, `repeat_count`만 9 vs 10 |

DMA 접근 패턴 자체는 깨끗하다. 예를 들어 HEADS=10의 활성값 소스는
`[0,0,k,0] [10,2,8,32] [2048,32,64,1]`로 batch 차원이 올바르게 표현되고,
출력은 **8개 DMA가 64열을 8열씩 분담**(`offset 0,8,...,56`, `sizes=[320,8]`,
320 = 10 heads × 32 rows)한다. 손상이 `col%8==0`이라는 것은 **그 8개 중 첫 번째
DMA(offset 0)에서만** 문제가 난다는 뜻이다.

⇒ **컴파일러가 만드는 구조에서 9와 10을 가르는 것이 없다.** (문제 ①과 같은 상황)

### M 통제 실험 — 행 반복은 무관, 총 작업량이 관련

HEADS를 고정하고 M(행 수)만 바꿨다:

| 구성 | 손상 원소 | 손상 head |
|---|---|---|
| b12, M=32 | 122 | h8(r%8=0), h10(r%8=2,4,6) |
| **b12, M=16** | 63 | **h8, h10 — 동일** |
| **b12, M=8** | 32 | **h8, h10 — 동일** |
| b10, M=32 | 31 | h8 |
| **b10, M=64** | **4152** | **h6, h8, h9 — 완전히 달라짐** (h9는 모든 행, 모든 열) |

관찰:

1. **M을 줄여도(32→16→8) 손상 head가 바뀌지 않는다.** M=8은 head당 행 타일이 1개뿐인데도
   같은 head가 손상된다 ⇒ **행 방향 반복은 원인이 아니다.**
2. 손상 **원소 수**는 M에 비례한다(M=8→32개, M=16→63개, M=32→122개) — 손상된 레인이
   모든 행에서 틀리기 때문.
3. **M을 늘리면(32→64) 손상 head가 완전히 달라진다**(h8 하나 → h6/h8/h9, 그리고 h9는
   전 범위로 번짐) ⇒ 손상 위치는 HEADS만의 함수가 아니라 **HEADS×M 규모(총 작업량/
   DMA 전송량)** 의 함수다.
4. b10/M=64에서는 열도 `%8`의 모든 값으로 번진다 ⇒ 규모가 커지면 "첫 레인만"이라는
   성질도 깨진다.

이는 문제 ①에서 확인한 "**per-dispatch DMA 전송량이 임계를 넘으면 발생**"과 같은 축이다.
다만 문제 ②는 **완전히 결정론적**이므로, 같은 규모에서는 항상 같은 자리가 틀린다.

## 5. 왜 이게 경합보다 먼저 볼 가치가 있나

| | 경합 (`proj2` 등) | 배치 레인 버그 |
|---|---|---|
| 재현성 | 확률적 (11/13 등) | **매번 100%** |
| 정적 근거 | 없음(코어 ELF·CDO·제어코드 전부 동일) | 규칙이 정확히 특정됨 |
| 영향 범위 | 24개 중 8개, 값 의존 | **배치 matmul 12개 전부** |
| 실제 BERT에서의 위치 | — | **attention의 핵심**(QK^T, Attn@V)이 배치 matmul |
| 디버깅 난이도 | 타이밍 의존, 개입이 시스템을 흔듦 | **결정론적 → 추적 쉬움** |

## 6. 남은 것 / 다음 단계

- **왜 head 8과 10인가**: batch=12가 `repeat_count`와 타일에 어떻게 매핑되는지 확인.
  head 8은 `(0,0)` 하나, head 10은 `(2,0),(4,0),(6,0)` 세 개라는 비대칭도 설명이 필요하다.
- **생성 코드 확인**: 배치 matmul dispatch의 코어 코드에서 8×8 누산기의 레인 저장/추출
  (`vst bmll0/bmlh0/bmhl0/bmhh0` 및 그 앞의 `aievec.matmul` 결과 재배치)을 본다.
  `proj2` 때와 같은 방법 — 다만 이번엔 결정론적이라 훨씬 수월하다.
- **`col%8==0`(첫 레인)이라는 점**이 가장 강한 단서다: 벡터 레인 0의 추출/저장 경로,
  또는 `aievec.matmul` 결과의 레인 재배치에서 첫 레인이 누락/덮어써지는지 확인할 것.
