# 근본 원인 후보 확정: 코어의 벡터 스토어 vs DMA 읽기 경합 (64B 단위 경계) — 2026-09-09

전날(`docs/2026-09-08_bug_localized_to_one_8x8_tile_of_proj2.md`)에 버그를 `proj2`의 단일
8×8 타일까지 국소화한 데 이어, 그 타일의 **입력을 tap**해서 손상이 어디서 생기는지 가르고,
행별 정확성 구조에서 **64바이트(=AIE2 벡터 레지스터 폭) 단위 진행 경계**를 찾은 기록이다.

---

## 1. 입력 tap — 손상은 dispatch 내부에서 생성된다

`proj2 = y1_DQ @ w0_2_DQ`의 8×8 타일 `[24:32, 520:528]`이 의존하는 것:

- **A 피연산자**: `y1_QuantizeLinear_Output[24:32, :]` (int8 활성값) — 실행마다 변할 수 있음
- **B 피연산자**: `w0_2_quantized[:, 520:528]` — **상수 initializer**, 실행 무관.
  실측: 전체 min −127 / max 109, 이 8열 블록은 min −86 / max 84, 포화(|w|=127) 0개.

`y1`은 Q/DQ 쌍의 **상류**라서 tap해도 QDQ→int8-matmul 융합이 깨지지 않는다(그래서 `y1_dq`나
int8 텐서 대신 `y1`을 골랐다). `y1`과 `proj2`를 같은 빌드에서 tap해 20회 실행:

| | 결과 |
|---|---|
| `y1` | **13/13 비트 동일** (단일 해시 `044bab825b`) |
| `proj2` | **6개 해시**, 11/13 쓰레기 타일 / 2/13 정상 |

`y1`이 비트 동일하면 `y1_q`도 비트 동일하다(quantize는 결정론적 elementwise). 가중치는 상수.
따라서 **두 피연산자가 완전히 동일한데 출력만 갈린다 → 손상은 `proj2` NPU dispatch 내부에서
생성된다.** (입력 오염 가설 배제.)

### 부수 발견 — int8 텐서를 그래프 출력으로 tap하면 런타임 assertion

`y1_QuantizeLinear_Output`(int8)을 그래프 출력에 추가하면 실행 시:

```
iree-run-module: runtime/src/iree-amd-aie/driver/amdxdna/buffer.cc:247:
  bool iree_hal_amdxdna_buffer_is_deallocated(iree_hal_buffer_t*):
  Assertion `IREE_UNLIKELY(!!(iree_hal_resource_is(base_buffer, &iree_hal_amdxdna_buffer_vtable)))' failed.
```

amdxdna HAL이 CPU(local-task) 측 버퍼를 받는 이종 device 구성 문제로 보인다. 별건이므로
f32 tap으로 우회했다. **앞으로 tap을 쓸 때 int8 텐서는 피할 것.**

## 2. 쓰레기값은 이 모델이 계산할 수 없는 크기다

NPU는 `int8 matmul → int32 acc → acc × (s_a·s_w)`. `s_a·s_w` = 0.00243499 × 0.00210634
= **5.129e-6**.

| | 값 |
|---|---|
| 이 타일 누산기의 이론적 최대치 (A가 전부 ±127) | **1,913,382** |
| 모델 전체 최대 누산기 (768×127×127) | 12,387,072 |
| 정상 누산기 (기준값에서 역산, 이 타일) | ≈ **4.3e4** |
| 쓰레기값이 함의하는 누산기 | **6.89e8** |

쓰레기는 타일 상한의 **360배**, 모델 전체 상한의 **55배**. 즉 "누산기가 안 지워진 채 정상
MAC이 더해졌다"로도 설명되지 않는다 — 애초에 누산 결과가 아니다.

**검토했지만 지지되지 않은 가설**: "int8 데이터가 int32로 잘못 해석됨". 함의된 int32를 4바이트로
쪼개면 전부 ±127 범위의 작은 값이라 그럴듯해 보였지만, 정량 비교에서 탈락 —
바이트 std 42.6 vs 실제 int8 텐서 std ≈ 24(가중치) / 25(활성값), 256바이트 중 15개가
|값|>100, 그리고 바이트 시퀀스가 `w0_2_quantized`/`y1_q` 어디에서도 발견되지 않음.

## 3. 결정적 구조 — 행별 정확성이 64바이트 경계에 딱 떨어진다

CPU 기준값 대비 **행별** 최대 오차를 그룹별로 계산(`.`=정상 <0.05, `p`=부분 <1, `X`=쓰레기 ≥1):

| 그룹 | n | r24 r25 r26 r27 r28 r29 r30 r31 | 패턴 |
|---|---|---|---|
| `db9d09d348` | 10 | X X p p . . . . | `XXpp....` |
| `d972b89ece` | 3 | X X p p . . . . | `XXpp....` |
| `e480c9b332` | 1 | X X p p . . . . | `XXpp....` |
| `f3e2e8aa36` | 1 | X X p p . . . . | `XXpp....` |
| `3dd2ec601e` | 1 | X X p p . . . . | `XXpp....` |
| `93e62e8581` | **4** | . . . . . . . . | **전부 정상** |

**모든 손상 그룹이 정확히 같은 패턴이다.** 행별 함의 누산기:

| 행 | 함의 누산기 | 정상 기준 ≈4.3e4 |
|---|---|---|
| 24, 25 | **6.89e8 / 6.71e8** — 모든 손상 그룹에서 동일 | 쓰레기 |
| 26, 27 | 3.5e3 ~ 7.8e3, 또는 **정확히 0** (2개 그룹) | 부분/미누산 |
| 28~31 | 2.6e4 ~ 4.5e4 | 정상 |

### 왜 2행 단위인가 — 벡터 스토어 폭

- 8열 × int32(4B) = **행당 32바이트**
- **2행 = 64바이트 = AIE2 벡터 레지스터 폭(512비트)**
- 8×8 int32 누산기(256B)는 **64B 벡터 스토어 4번**으로 L1에 기록된다

관측된 경계가 정확히 그 스토어 단위에 떨어진다:

```
스토어 0 (행 24-25)  미완료      → 잔여 데이터(쓰레기, 6.89e8)
스토어 1 (행 26-27)  진행 중     → 0 또는 부분값
스토어 2-3 (행 28-31) 완료       → 정상
```

## 4. 진단

**코어가 8×8 int32 누산기를 L1 출력 버퍼에 벡터 스토어로 기록하는 도중에, DMA가 그 버퍼를
읽어나가고 있다.** 즉 코어의 스토어가 완료·가시화되기 전에 "데이터 준비" lock이 release되는
**메모리 fence 누락**(또는 lock release 순서 보장 누락)이다.

이 진단이 설명하는 것:

| 관측 | 설명 |
|---|---|
| 손상 단위가 정확히 8×8 타일 | 코어 1개의 L1 출력 버퍼 = 8×8 int32 = 256B |
| 손상 경계가 2행(64B) 단위 | 벡터 스토어 1회 = 64B |
| 쓰레기값이 실행마다 동일(6.89e8) | 그 L1 위치의 잔여 데이터가 결정론적 |
| 앞쪽 행이 쓰레기, 뒤쪽 행이 정상 | DMA가 버퍼 앞에서부터 읽기 시작해 초반엔 코어를 앞지르고, 이후 코어가 추월 |
| 두 피연산자는 비트 동일 (§1) | 경합은 출력 handoff에서 발생 |
| 버그 #1의 10k-cycle busy-wait가 "고쳤던" 것 | 스토어가 착지할 시간을 준 것 — 전형적인 fence-누락 우회 |
| int8 + 벡터화에서만 재현 | 벡터화 코어는 타일을 소수의 wide store로 쓰고 requantize 에필로그가 짧아 창이 좁고 타이트 |
| 내 memtile gather 패치가 무효했던 이유 | 그 패치는 memtile 측 producer 신원을 고쳤을 뿐, **코어→L1 handoff**는 건드리지 않음 |

즉 이것은 **버그 #1(batch-0 all-zero)의 진짜 근본 원인이 `1600078`의 delay로 가려진 채
살아남아, delay가 덮지 못하는 지점에서 다시 나타난 것**으로 보인다. 사용자가 처음에 물었던
"버그 #1이 재발한 것 아닌가"라는 의심과 일치한다.

## 4-b. fence 확인 — 그리고 최소 지연으로 비결정론이 사라짐

### Peano 자체 lock 헤더가 이미 힌트를 준다

`llvm-aie/lib/clang/19/include/aie2p_locks.h`:

```c
// Acquire and release instructions considering a memory pointer
// The below definitions with ptr arg is not officially used anywhere.
// The ptr arg is intentionally not used.          ← 버퍼 포인터 의존성을 의도적으로 버림
INTRINSIC(void) release(void *a, unsigned id, int val) { return release(id, val); }

INTRINSIC(void) done(void) {
  __builtin_aie2p_sched_barrier();                 ← done()에는 배리어가 있는데
  __builtin_aie2p_done();
  __builtin_aie2p_sched_barrier();
}
INTRINSIC(void) release(unsigned id, int val) { return __builtin_aie2p_release(id, val); }
                                                   ← release()에는 없음
```

AMD가 **컴파일러에 메모리 의존성을 보여줄 수 있는 포인터 인자 변형을 설계해두고 쓰지 않는다.**
그리고 `sched_barrier`는 존재하며 `done()`에는 쓰지만 `release()`에는 없다.
IREE 측에서도 lock 함수는 `AMDAIECoreToStandard.cpp`에서 `func.func private`로 **아무 메모리
효과 속성 없이** 선언된다.

### 생성 코드 확인 — 누산기 스토어는 정확히 4×64B, release까지 ~10 번들

`--iree-hal-dump-executable-files-to`로 코어 ELF를 뽑아 `llvm-objdump --triple=aie2p`:

```
      aa: vst bmll0, [p3, #0x0]     ← 바이트 0~63     → 행 24-25
      ae: vst bmlh0, [p3, #0x40]    ← 64~127          → 행 26-27
      b4: vst bmhl0, [p3, #0x80]    ← 128~191         → 행 28-29
      ba: vst bmhh0, [p3, #0xc0]    ← 192~255         → 행 30-31
      c0..dc: 5~6 번들 (루프 제어)
      e0: ret lr
   호출자: acq #0x31 → movxm ×3 → rel #0x32          ← 4~5 번들
```

**§3의 `XXpp....` 경계가 이 네 스토어의 오프셋과 정확히 일치한다.** 그리고 마지막 스토어부터
release까지 **약 10 명령 번들**뿐이며, 중간의 `acq`는 lock이 이미 available이면 즉시 통과하므로
신뢰할 수 있는 배리어가 아니다. **프로그램 순서는 이미 스토어→release로 올바르다** — 즉
컴파일러 재배치 문제가 아니라 **하드웨어 스토어 가시성 지연** 문제다.

### 정적으로는 실패 dispatch를 구별할 수 없다

손상 코어는 특정된다: 행 24-31 → AIE row 5, 열 520-527 → column 5 ⇒ **tile (5,5)**.
레이어 0/1/2의 비배치 matmul dispatch(각각 `dispatch_1`/`_5`/`_9`)를 비교하면:

| 아티팩트 | d1 (레이어0, 정상) | d5 (레이어1, 정상) | d9 (레이어2, 손상) |
|---|---|---|---|
| `core_*.elf` 32개 전부 | 동일 | 동일 | **동일** |
| `aie_cdo_init/enable/elfs.bin` | 동일 | 동일 | 동일 |
| `aie_cdo_switches.bin` | (다름) | 동일 | 동일 |
| `npu_inst.txt` | 615줄 | 615줄 | 615줄, **d5와 16줄만 다름 — 전부 호스트 버퍼 주소**(`0009C1xx`→`001381xx`) |

**정적으로 레이어 2를 구별하는 것이 없다.** 스케일 상수는 코어 코드에 박히지 않으므로
"스케일이 명령 스케줄을 바꾼다"는 가설도 반증됐다. 트리거는 순전히 동적이다.

### 결정적 실험 — release **앞**에 최소 지연

기존 두 실험 블록은 (1) 첫 release **뒤**(`1600078`, 항상 켜짐), (2) 첫 acquire **앞**
(env-var, 다른 가설용)이다. **"release 앞"은 시도된 적이 없었다** — 그런데 스토어 가시성
문제라면 지연은 바로 거기 있어야 한다(release 뒤는 가시성에 아무 도움이 안 된다).

`AMDAIECoreToStandard.cpp`에 세 번째 실험 블록을 추가했다(env-var `AMDAIE_EXPERIMENTAL_PRE_RELEASE_DELAY`,
opt-in이라 기본 빌드 불변): **모든** release 바로 앞에 busy-wait 삽입, 반복 횟수는 env 값(기본 100).
디스어셈블로 삽입 확인 — 루프 카운트 `r10 = 0x19 = 25`(=100/4 언롤)가 `rel #0x32` 앞에 위치.

`chainmix_L12_y1p2` (= `y1` + `proj2` tap, 재현 확인된 모델), CPU 기준값 대비:

| | `proj2` err-vs-ref | `proj2` 실행간 편차 | `y1` 편차 | 쓰레기 타일 |
|---|---|---|---|---|
| **기준선** | 0.1677 ~ **3532** | **3532** | 0 | **11/13** |
| 지연 100 (20회) | 0.1915 (일정) | 0.0413 | 0.0170 | **0/20** |
| **지연 8 (18회)** | **0.1915 (일정)** | **0** | **0** | **0/18** |

- **지연 100**: 쓰레기 타일은 완전히 제거되지만, *모든* release(입력 버퍼 해제 포함)를 늦춰
  전역 타이밍이 바뀌면서 `y1`을 비롯해 없던 경미한 변동(~5%)이 생겼다. 진단용으로는 유효하지만
  깨끗한 실험은 아니다.
- **지연 8**: **쓰레기 타일 제거 + 모든 tap에서 실행간 편차 정확히 0.** `y1`/`proj2`/`y_final`
  전부 18회 비트 동일.

정식 재현 아티팩트(tap 없는 `chainmix_L12_int8`)로도 확인: **40회 → 1개 비트 패턴, 완전
결정론**(기준선은 40회 → 5개 패턴).

### ⚠️ 그런데 통제 실험이 이 결과를 confound시킨다

원래 **버그가 전혀 없던** clean 인스턴스(`L12_s0`: 기준선에서 20/20 결정론적이고 모든 tap이
정확)에 같은 지연을 넣어보면:

| `L12_s0` | corr (float 기준) | 결정론 |
|---|---|---|
| 기준선 (지연 없음) | **0.9736** | 20/20 |
| pre-release 지연 8 | **0.9031** | 6/6 |

**버그가 없던 모델에서도 정확도가 떨어진다.** 즉 이 지연은 순수한 타이밍 shim이 아니라
**계산되는 값 자체를 바꾼다.** 가장 그럴듯한 이유는 삽입 방식이다 — `LLVM::AllocaOp` +
모든 release 앞에서 **기본 블록 분할** + volatile store 루프는 레지스터 압력과 명령 스케줄을
바꾸고, 코어의 하드웨어 루프 구조에도 영향을 줄 수 있다.

같은 열화가 dirty 인스턴스에서도 보인다: 정식 재현 아티팩트의 corr이 기준선 정상 실행의
0.970에서 **0.897**로, tap 모델의 `y_final` err-vs-ref는 0.3875 → **0.6349**로 나빠진다.
(양쪽 지연 값 8/100에서 동일하므로 지연 길이가 아니라 삽입 자체의 영향이다.)

**따라서:**

- ✅ **확정**: §1~3의 측정(8×8 타일, 64B/벡터-스토어 단위 `XXpp....` 경계, 피연산자 비트 동일,
  쓰레기가 누산 결과일 수 없음, 생성 코드의 4×64B 스토어와 ~10 번들 창)은 모두 관측이며 유효하다.
- ✅ **확정**: release 앞에 분리를 넣으면 비결정론과 ±3532 쓰레기 타일이 사라진다(40/40, 18/18).
- ⚠️ **미확정**: 그것이 **스토어 가시성 때문**이라는 인과. 개입이 수치를 바꾸므로 "스토어가
  착지할 시간을 줬다"와 "삽입이 코드를 바꿔 우연히 경합을 회피했다"를 구분할 수 없다.
  **이 지연은 fix가 아니다.**

### 중립 개입 3종 시도 — 순서는 문제가 아니고, 필요한 건 "시간"이다

`alloca`/블록분할 없는 중립 개입을 세 가지 시도했다.

**(1) 인라인 어셈블리 `nop` — 불가능.** Peano(llvm-aie)는 aie2p에서 **인라인 asm을 전혀
지원하지 않는다.** 가장 단순한 `__asm__ volatile("nop")`조차 Peano clang에서
`unable to translate instruction: call` (GlobalISel IRTranslator)로 죽는다. aie2p 빌트인
141개 중 `nop`/지연 계열도 **없다**.

**(2) 직선 volatile store — 중립성 검증 실패, 그리고 그 실패가 더 중요하다.**
`alloca`를 함수 진입부로 1개만 hoist하고 블록 분할 없이 store 8개를 직선으로 넣었다
(디스어셈블 확인: `st r8, [p6, #0]` ×8 → `rel #0x30`). 그런데 **원래 완벽했던 clean
인스턴스가 깨졌다:**

| `L12_s0` | 결과 |
|---|---|
| 기준선 | **20/20 비트 동일**, corr 0.9736 |
| 직선 store 8개 | **6회 중 5개 패턴 — 비결정론적**, corr 0.942~0.976 |

원인은 포인터 레지스터(`p6`)를 코어 함수 전체에 걸쳐 살려두면서 레지스터 할당이 바뀌는 것으로
보인다. **함의: 완벽히 결정론적이던 모델이 release 앞에 몇 사이클 넣는 것만으로 비결정론이
된다 — 이 설계는 한 곳의 결함이 아니라 여러 handoff가 전부 타이밍 여유가 거의 없는 상태다.**
그래서 "clean 인스턴스"들은 견고하게 안전했던 게 아니라 **여유 경계의 안전한 쪽에 우연히
놓여 있었을** 가능성이 크고, 앞서 관찰한 인스턴스 의존성도 그 경계의 어느 쪽에 떨어지는지의
문제로 읽는 것이 자연스럽다.

**(3) `sched.barrier` — 중립성 증명 + 버그 미수정.** 유일하게 진짜 중립인 개입이다.
Peano clang으로 확인: `llvm.aie2p.sched.barrier()`는 **어셈블리에 명령을 전혀 추가하지 않는다
(0 사이클)**, 피연산자·결과가 없어 **레지스터 0개**, 블록 분할도 없다.

| 검증 | 결과 |
|---|---|
| clean 인스턴스 중립성 | **해시 `0fc25b14b30a` = 기준선과 비트 동일**, 6/6 결정론, corr 0.973568 동일 ✅ |
| dirty 인스턴스 타일 | **19회 중 16회 여전히 쓰레기** (기준선 11/13과 사실상 동일) ❌ |

### 결론 — 두 메커니즘이 깔끔하게 분리됐다

| 개입 | 중립성 | 쓰레기 타일 |
|---|---|---|
| `sched.barrier` (0 사이클, 순서만 고정) | ✅ 비트 동일 (증명) | ❌ 미수정 |
| busy-wait 루프 (사이클 추가) | ❌ clean 인스턴스 corr 0.9736→0.9031 | ✅ 수정 |
| 직선 volatile store (사이클 추가) | ❌ clean 인스턴스가 비결정론이 됨 | ✅ 수정 |

1. **순서(ordering/스케줄링)는 원인이 아니다.** 0비용 순서 배리어가 아무 효과가 없다 —
   디스어셈블에서 이미 스토어→release 순서였던 것과 일치한다.
2. **필요한 것은 "시간"이다.** 사이클을 넣는 두 방식만 타일을 고친다 ⇒ §4의 스토어 가시성
   (하드웨어 지연) 읽기를 **지지한다**.
3. **그런데 이 툴체인에는 그 시간을 넣을 깨끗한 수단이 아예 없다** — 인라인 asm 미지원,
   nop/지연 빌트인 없음, Chess `chess_separator()` 계열은 Peano 헤더에서 빈 매크로,
   `sched.barrier`는 순서 전용(0 사이클). **이것이 이번 조사에서 특정한 툴체인 공백이다.**
4. **동시에, 사이클을 넣는 어떤 방식도 전역 타이밍을 흔들어 다른 곳의 경합을 연다**
   ((2)에서 clean 인스턴스가 깨진 것). 따라서 "release 앞 지연"은 **fix가 될 수 없다** —
   한 경합을 다른 경합과 맞바꾸는 것이다.

### 그래서 남은 진짜 선택지

- **컴파일러/툴체인 쪽**: Peano에 aie2p용 지연/`nop` 수단(또는 lock release 앞 store-visibility
  보장)을 요청·추가하는 것. 지금은 IREE에서 표현할 방법이 없다.
- **구조 쪽**: 사이클로 창을 좁히는 대신, 코어의 출력 버퍼 handoff 자체를 경합이 불가능한
  형태로 바꾸는 것(예: 코어가 스토어 완료를 확인할 수 있는 경로, 또는 더 깊은 버퍼링으로
  DMA가 앞지를 수 없게 만드는 것).
- 어느 쪽이든 **"clean 인스턴스가 여유 경계에 걸쳐 있다"**는 (2)의 발견 때문에, 이 모델만
  고쳐서는 안 되고 handoff 전반의 여유를 봐야 한다.

### 다음 단계 — 수치적으로 중립인 개입이 필요하다

- `alloca`/블록 분할/루프를 쓰지 않고, **의미상 no-op인 것만** 삽입한다: Peano의
  `__builtin_aie2p_sched_barrier()`에 대응하는 intrinsic 호출, 또는 고정 개수의 `nop`.
  그러면 레지스터 압력과 블록 구조가 바뀌지 않아 수치가 보존되고, 인과를 깨끗하게 가릴 수 있다.
- 중립성 검증은 clean 인스턴스(`L12_s0`)로 한다: **개입 후에도 corr 0.9736과 비트 동일**해야
  비로소 그 개입이 타이밍만 바꿨다고 말할 수 있다.
- 그 상태에서 dirty 인스턴스의 쓰레기 타일이 사라지면 §4 진단이 확정된다.
- 부수적으로: Peano `release()`의 **포인터 인자 변형을 실제로 사용**하는 것도 시도 가치가 있다
  (컴파일러에 메모리 의존성을 노출 — 다만 프로그램 순서는 이미 맞으므로 하드웨어 지연에는
  효과가 없을 수 있다).

주의(정직하게): 지연을 넣은 빌드는 `y_final`의 CPU 기준값 대비 오차가 오히려 커진다
(0.3875 → 0.6349, 두 지연 값 모두 동일). 기준선의 0.3875는 손상 + 하류 int8 포화가 섞인
값이라 직접 비교할 수 없지만, **12레이어 int8 체인의 NPU-vs-CPU 계통 오차 자체가 큰지는
별도 확인이 필요하다**(이번 버그와 무관한 정확도 문제일 수 있음).

## 5. 아직 설명되지 않은 것

- **왜 하필 이 타일/이 dispatch인가.** 12개 비배치 dispatch는 구조가 동일하고 `proj0`/`proj1`은
  정확하다. 경계가 거의 결정론적인 것도 특이하다(타이밍이 거의 고정).

  값이 타이밍을 바꿀 경로가 자명하지 않다.
- 4/22 실행이 완전히 정상인 조건.
