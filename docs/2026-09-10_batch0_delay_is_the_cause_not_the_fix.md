# `1600078`의 batch-0 delay가 배치 matmul을 틀리게 만든다 — 2026-09-10

전날 찾은 "배치 int8 matmul 12개가 전부 항상 틀린다"(문제 ②,
`docs/2026-09-09_batched_int8_matmul_deterministic_lane_bug.md`)를 파던 중,
사용자의 질문 — *"팀원이 분석 중인 batch-0 all-zero 증상과 다른 문제인가?"* — 에서 출발해
**원인이 우리 쪽 우회책(`1600078`)이라는 것**을 확인했다.

**결론부터: ②의 원인은 upstream 컴파일러 버그가 아니라, batch-0 증상을 덮으려고 넣은
delay 자체다. 그리고 그 delay를 끄면 batch-0 증상도 재현되지 않는다.**

---

## 1. 왜 이걸 확인하게 됐나

②의 모든 측정은 **delay가 켜진 빌드**에서 이뤄졌다. `1600078`이 기본 빌드에 무조건
들어가 있었기 때문이다(env-var 게이트 없이 `{`로 시작하는 블록).

그래서 "delay가 batch 0만 덮고 head 8/10은 못 덮어서 ②가 남은 것인가?"를 가리려고
delay를 끌 수 있게 만들었다:

```cpp
// AMDAIECoreToStandard.cpp — 기본 동작은 불변, opt-out만 추가
if (!::getenv("AMDAIE_DISABLE_BATCH0_DELAY")) { ... }
```

## 2. 결과 — delay를 끄면 ②가 사라진다

### 최소 재현체 (`bmmlane_b12_m32_k64_s0`, dispatch 1개)

| | vmfb 크기 | 손상 원소 |
|---|---|---|
| delay **ON** | 156,753 | **122개** (h8/r%8=0, h10/r%8=2,4,6, 전부 col%8==0) |
| delay **OFF** | 140,897 | **0개 — 완전 정확** |

같은 빌드, 같은 모델, env-var 하나 차이다. delay ON은 두 번 컴파일해 같은 결과를 확인했다.

### 실제 chainmix (bmm 12개 전수, 8회 실행)

| | 오차 최소~최대 | 실행간 편차 |
|---|---|---|
| delay **ON** (전날 측정) | 0.1235 ~ 0.4521 | 0.0024 ~ 0.081 (6개 단계) |
| delay **OFF** | **0 ~ 1.192e-07** | **전부 0** |

**12개 배치 matmul 전부가 delay를 끄면 비트 수준으로 정확해진다.**

### 원래 batch-0 아티팩트 (`bmm12_int8`, 8/24에 쓰인 것)

| | 결과 (4회 실행) |
|---|---|
| delay **ON** | **batch 10에서 오차 0.02629** (4/4 동일) |
| delay **OFF** | **전부 정확** |

## 3. batch-0 all-zero 증상은 재현되지 않는다 — 원본 재현체로도 확인

### 8/24 원본을 바이트 단위로 복원해서 확인

`_local/int8_debug/gen_and_quant_bmm.py`(8/24 당시 스크립트, `B,M,K,N = 2,16,16,64`,
`default_rng(0)`)를 그대로 재실행해 **원본 `bmm_int8.onnx`와 바이트 단위로 동일한**
모델을 재생성했다. 두 피연산자 모두 런타임 입력이고 calibration 스케일까지 같다.

| | 결과 (각 6회) |
|---|---|
| **delay OFF** | 6/6 **전부 정확** — batch 0 정상 |
| **delay ON** | 6/6 전부 정확 |

**delay 없이도 batch 0이 all-zero가 아니다.**

### 규모별 정리 — delay는 큰 모델에서만 해를 끼친다

| 모델 | delay OFF | delay ON |
|---|---|---|
| 8/24 원본 (B=2, M=16) | 정확 | 정확 |
| `bmm12_int8` (B=12, M=32, 입력 2개) | 정확 | **batch 10 오차 0.02629** |
| 최소 재현체 (B=12, M=32, 가중치 상수) | 정확 | **h8·h10 손상 122개** |
| chainmix bmm 12개 | 정확 (0~1.2e-07) | **전부 오차 0.12~0.45** |

작은 모델에서는 delay가 무해하고, **규모가 커지면 손상을 만든다.**

### ⚠️ 호스트 부하가 측정을 망칠 수 있다 (측정 방법 교훈)

첫 시도에서 이 재현체가 **6회 시도 전부 출력을 남기지 못했다**(실행당 ~60초, TDR
타임아웃 패턴). 원인은 버그가 아니라 **호스트 부하**였다 — 당시 다른 사용자의
`cpptools`(IDE C++ 인덱서)가 **CPU 790%**(코어 8개 분량)를 쓰고 있었다. 조용해진 뒤
같은 명령이 12/12 정상 실행됐다.

`scripts/lock/`은 NPU와 빌드만 직렬화하므로 IDE 인덱싱 같은 부하는 락에 걸리지 않는다.
그래서 `scripts/lock/host-load.sh`를 추가했다 — `/proc/stat` 델타로 **순간** CPU를 재고
(ps의 `%cpu`는 프로세스 수명 평균이라 이미 끝난 스파이크를 계속 높게 보여준다: 같은
순간에 ps 591% vs 실측 224%), 내 것을 제외한 타 사용자 부하로 `OK`/`NOISY`/`BUSY`를
판정한다. **타이밍에 민감한 실험 전에는 이걸 먼저 확인할 것.**

## 3-b. (이전 절) 다른 조건들에서도 재현 안 됨

원래 시작점이었던 "batch index 0이 always all-zero"를 delay OFF로 여러 조건에서 찾아봤다:

| 모델 | delay OFF 결과 |
|---|---|
| `bmm12_int8` (원래 아티팩트, 입력 2개) | 전부 정확 |
| `bmmlane b2 · M=16` | 전부 정확 |
| `bmmlane b4 · M=16` | 전부 정확 |
| `bmmlane b12 · M=16` | 전부 정확 |
| `bmmlane b12 · M=32` | 전부 정확 |
| chainmix bmm 12개 | 전부 정확 |

**어디서도 batch 0이 all-zero로 나오지 않는다.** 원래 기록(`docs/2026-08-24_...` §5)의
조건 — `M=16`, batch=2/4 — 을 맞춰봐도 재현되지 않았다.

### 재현체 차이 하나는 확인했다

내가 만든 `gen_bmm_lane_repro.py`는 **가중치가 컴파일 시 상수**(코어에 내장)인데,
원래 `bmm12_int8`은 **입력이 2개**(`[12,32,32] @ [12,32,64]`)로 **가중치도 런타임 DMA**로
들어온다. 그 DMA 경로 유무가 다르다.

그래서 원래 아티팩트로도 직접 돌렸는데(위 표), 그쪽에서도 batch-0 증상은 안 나왔고
delay ON일 때 batch 10이 틀리는 것만 나왔다.

## 4. 그래서 지금 알 수 있는 것 / 알 수 없는 것

### 확정 (재현 가능)

1. **delay ON이 배치 matmul을 틀리게 만든다.** 3개 독립 모델(최소 재현체, chainmix,
   원래 bmm12)에서 모두, delay를 끄면 정확해진다.
2. **delay OFF에서 배치 matmul은 비트 수준 정확하다** (오차 0 ~ 1.2e-07).
3. 손상 패턴이 값·레이어·입력에 무관하게 고정된 것도 이제 설명된다 — 데이터가 아니라
   **삽입된 코드**가 원인이므로 당연히 결정론적이다.

### 미확정 — 중요

4. **원래 batch-0 all-zero 증상을 재현하지 못했다** — 원본 스크립트를 바이트 단위로
   복원해서 delay OFF로 돌려도 정확하다. 따라서 "delay가 불필요하다"고 단정할 수 없다.
   가능한 설명:
   - (a) 그 증상을 내는 정확한 조건(모델/플래그/컴파일러 리비전)을 아직 복원하지 못함
   - (b) 8/24 이후 컴파일러에 들어간 다른 수정들이 그 증상을 이미 해결했고, delay만
     부작용으로 남아 있음
   - (c) 원래 관측 자체가 다른 원인(당시의 다른 버그)이었을 가능성

   **채널 배정 가설은 반증했다**: `0baac08`+`3509353`(`AMDAIEAssignChannels.cpp` +329줄,
   `ChannelGenerator` +66줄)을 8/25 상태로 되돌려 빌드했더니, 이 모델들의 vmfb가
   **바이트 단위로 동일**했다. 그 수정들은 packet-flow 전용이고 우리 배치 matmul은
   circuit 경로를 쓰므로 생성 코드에 영향이 없다. (하드웨어 테스트 없이 결론)

   또한 **전체 리비전 되돌리기는 불필요**하다: 8/25와 현재의 IREE 서브모듈 차이는
   커밋 1개·파일 1개·9줄(bias fusion 전용)이고 llvm-project는 동일하다. AMD-AIE 플러그인
   쪽에도 배치 matmul 경로를 건드리는 커밋이 보이지 않는다.
5. delay가 **왜** 배치 matmul을 깨뜨리는지의 메커니즘. 유력한 가설: delay는 `alloca` +
   기본 블록 분할로 런타임 루프를 삽입하는데, 이것이 레지스터 배치와 명령 스케줄을 바꾼다.
   (같은 성질을 별개 실험에서 이미 확인했다 — 직선 store 8개만 넣어도 20/20 결정론적이던
   모델이 6회 중 5패턴으로 깨졌다.) 배치 matmul은 코어당 타일 6개를 순차 처리하므로 그
   루프 구조가 특히 민감할 수 있다.

## 5. 정정하는 이전 결론

| 이전 서술 | 정정 |
|---|---|
| "배치 matmul은 upstream 컴파일러의 순수 구조적 코드 생성 버그" | **우리가 삽입한 delay의 부작용.** 값 무관·결정론적인 건 맞지만 원인이 우리 패치다 |
| "bmm은 어떤 조건에서도 작동하지 않는다" | **delay만 끄면 정확하다** |
| "delay는 batch-0을 고친 workaround" | 최소한 현재 컴파일러에서는 **고치는 대상이 재현되지 않고, 부작용만 관측된다** |

## 6. 다음 단계

1. **팀원에게 직접 확인한다 (가장 빠름)**: "batch 0 = 0 증상을 지금도 재현할 수 있나요?
   어떤 모델·조건인가요?" — 그 증상의 근본 수정을 맡고 있는 사람이 조건을 알고 있을
   가능성이 높다. 원본 스크립트·리비전·채널 배정은 이미 다 확인했으므로, 남은 건
   당시 실험의 다른 맥락(BERT-tiny 2레이어 전체 등)이다.
2. 재현되지 않으면 **delay 제거를 검토한다** — 그 경우 delay는 순손실이다.
3. 재현되면 **delay 없이 근본 원인(lock pre-charge)을 고치는 쪽으로** 간다. 팀원이 이미
   그 작업을 맡고 있고, 이 결과가 그 필요성을 강하게 뒷받침한다.
4. §4-5의 메커니즘(왜 delay가 배치 matmul을 깨뜨리는가)은 코어 ELF를 delay ON/OFF로
   디스어셈블 비교하면 직접 볼 수 있다.

## 재현 방법

```bash
# delay OFF로 컴파일 (기본은 ON, 동작 불변)
AMDAIE_DISABLE_BATCH0_DELAY=1 build/tools/iree-compile <mlir> -o <vmfb> <플래그...>
```
