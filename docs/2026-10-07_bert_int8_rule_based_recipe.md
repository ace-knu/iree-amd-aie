# BERT int8 — 규칙으로 정하는 양자화 레시피 (2026-10-07)

지금까지의 정확도 작업은 BERT 를 돌려 보고 결과가 나쁜 곳을 고르는 방식이었다(SmoothQuant α = 0.6,
per-channel 은 FC1·FC2 만, GELU 출력만 비대칭). 통합 컴파일러에 넣으려면 어떤 모델이 들어와도 같은 규칙으로
같은 결정이 나와야 한다. 이 문서는 그 결정들을 **그래프 구조와 보정 데이터만 보는 규칙**으로 바꾼 결과다.
평가 64 문장은 규칙을 정하는 데 쓰지 않았다.

이전 단계: `docs/2026-10-07_bert_int8_gelu_asymmetric.md` (GELU 출력 비대칭, NPU 0.9690).

---

## 0. 요약

| | 이전 (결과 보고 고름) | 규칙 레시피 | **+ GELU 하한 규칙** |
|---|---:|---:|---:|
| ORT, 64 문장 (배포 모델) | 0.9697 | 0.9785 | **0.9852** |
| **NPU, 64 문장** | 0.9690 (최저 0.9624) | 0.9773 (최저 0.9683) | **0.9845** (최저 0.9796) |
| NPU − ORT | −0.0007 | −0.0012 | −0.0007 |
| 1 회 추론 (중앙값, 2 회) | 333 / 332 ms | 332 / 332 ms | 334 / 334 ms |

- 규칙만으로 이전 레시피보다 **+0.0083**, 64 문장 **전부** 좋아졌다. 속도는 같다.
- 결정을 바꾼 것은 α 다. 위치마다 보정 데이터의 matmul 출력 오차가 가장 작은 α 를 고르니 0.65 ~ 0.95 가
  나왔다. 0.6 은 가중치가 per-tensor 이던 시절에 고른 값이다.
- 컴파일러는 바꾸지 않았다. 이전 커밋(`1d3322e0`)까지의 컴파일러로 컴파일되고 돈다.
- NPU − ORT 가 이전보다 0.0005 커졌다. NPU softmax ukernel 이 큰 확률을 1 ~ 2 LSB 작게 내는 오차에 이 레시피가
  더 민감하기 때문이다(§6). 두 레시피 공통의 약 −0.0008 은 원인을 찾지 못했다.
- 규칙 레시피에서 연산별로 int8 을 fp32 로 되돌려 보니 남은 오차의 절반 가까이가 **FC1 출력(GELU 입력)** 에
  있었다(§7). 대칭 scale 이 GELU 가 0 을 내는 음수 꼬리(−60 까지)를 덮느라 거칠어진 것이다.
- **GELU 하한 규칙**(§8): 텐서를 쓰는 곳이 GELU 하나뿐이면 양자화 하한을 GELU 포화점 −4 로 올린다. NPU
  0.9773 → **0.9845**, 64 문장 전부 개선, 속도 +2 ms. 컴파일러는 바꾸지 않았다.

## 1. 레시피를 정하는 규칙

| 결정 | 이전 | 규칙 |
|---|---|---|
| SmoothQuant 위치 | LayerNorm 출력 + 노드 이름 `intermediate_act_fn/Mul_1` | 상수 가중치 MatMul 의 입력이면서, 만든 연산이 LayerNorm 이거나 elementwise 인 텐서. LayerNorm 은 γ/β 로 흡수, 그 밖은 Mul 을 넣는다 |
| α | 전 위치 0.6 (평가 결과로 고름) | 위치마다 보정 데이터의 matmul 출력 상대 오차가 가장 작은 값 (§3) |
| 가중치 | FC1·FC2 만 per-channel | 모든 MatMul per-channel, 단 컴파일러 지원 범위 안 (§4) |
| 비대칭 | 텐서 이름 `sq_x_N` (GELU 출력) | 대칭 대비 scale 이 1.25 배 이상 줄고 컴파일러가 지원하는 위치 |
| 보정 | 백분위 99.999, 보정 90 문장 | 그대로 |
| 소비자 포화 (§8) | 없음 | 텐서를 쓰는 곳이 GELU 하나뿐이면 하한 = −4, 상한 = 127·scale 그대로, 비대칭 |

**"컴파일러 지원 범위 안"** 이 규칙의 일부다. 지금 지원 범위:
- 활성값 zero-point: 상수 가중치 per-channel matmul 의 입력이면서 LayerNorm 출력이 아닌 텐서
  (LayerNorm matcher 는 출력 zero-point 0 만 받는다).
- per-channel 가중치: head split 되는 Q/K/V 는 제외 (§4).

|---|---:|---:|

| α 0.6 + 구조 규칙 SQ + 전부 pc (비대칭 없음) | 0.9481 | 0.9372 |
| α 0.5 + 구조 규칙 SQ + 전부 pc + 통계 규칙 비대칭 | 0.9429 | 0.9333 |
| α 0.5 + 구조 규칙 SQ + 전부 pc (비대칭 없음) | 0.8187 | 0.6804 |

- 구조 규칙은 SmoothQuant 위치 36 곳(LN 24, GELU 12)을 이름 기반과 똑같이 골랐다.
- α 0.6 에서 통계 규칙 비대칭은 GELU 출력 12 곳만 골랐다(이름 기반과 같다).
- 모든 MatMul per-channel 은 FC1·FC2 만일 때와 같거나 조금 낫다.
- 비대칭을 지원 여부와 관계없이 모든 활성값(softmax, LN 출력, matmul 출력 등)에 걸면 오히려 나빠졌다.
  원인은 보지 않았다.
- α 를 하나로 맞추면 평균은 0.003 낮고 최저 문장이 크게 떨어진다.

## 3. α 를 보정 데이터로 고르는 규칙

위치 t(입력 X, 소비하는 상수 가중치 W 를 열 방향으로 이어 붙인 것)마다, 후보 α 에 대해

```
s_j  = max|X_j|^α / max|W_j|^(1−α)              (smooth.py 와 같은 식)
err(α) = ‖ Q_act(X / s) · Q_w(diag(s) W) − X W ‖² / ‖ X W ‖²
```

를 보정 90 문장의 실제 토큰 위치에서 재고 가장 작은 α 를 고른다. `Q_w` 는 per-channel 대칭 int8,
`Q_act` 는 백분위 99.999 대칭 int8 이고, 비대칭 규칙에 걸리면 비대칭이다 — 레시피 그대로다.
후보는 0.4, 0.5, 0.6, 0.65, 0.7, 0.75, 0.8, 0.85, 0.9, 0.95. 처음 0.3 ~ 0.8 로 했을 때 대부분이 끝값 0.8 을
골라 범위를 넓혔고, 넓힌 뒤에는 안쪽에서 정해진다.

고른 α 의 분포:

| 위치 | 0.65 | 0.7 | 0.75 | 0.8 | 0.85 | 0.9 | 0.95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| LayerNorm 출력 (24) | | 3 | 6 | 2 | 8 | 3 | 2 |
| GELU 출력 (12) | 2 | | 2 | 2 | 4 | | 2 |

GELU 출력 층 0 ~ 11: 0.8, 0.85, 0.85, 0.95, 0.75, 0.75, 0.8, 0.85, 0.95, 0.65, 0.65, 0.85.

전 위치 오차 합: 0.4 → 0.158, 0.5 → 0.074, 0.6 → 0.041, 0.7 → 0.026, 0.8 → 0.0215, **0.85 → 0.0210**,
0.9 → 0.0257, 0.95 → 0.0250.

α 가 커지면 GELU 출력의 치우침이 줄어, 통계 규칙 비대칭이 12 곳에서 **9 곳**(층 0, 1, 2, 4, 5, 6, 7, 9, 10)으로
줄었다. 층 3, 8, 11 은 scale 감소가 1.25 배 미만이라 대칭으로 남았다.

## 4. Q/K/V 가 per-tensor 로 남는 이유

배포 경로의 `head_split.py` 는 Q/K/V 가중치 `[K, H·D]` 를 헤드별 `[H, K, D]` 로 재배치한다. per-channel scale
은 그러면 `[H, 1, D]` 가 되는데 ONNX DequantizeLinear(opset 17)는 1 차원 per-axis scale 만 받고, 컴파일러의
per-channel 접기도 scale 이 batch(헤드)마다 다른 경우를 받지 않는다. 그래서 head split 되는 matmul(출력이
Reshape → Transpose 로 헤드를 나누는 것, 구조로 판단)은 per-tensor 로 둔다.

| ORT, 64 문장 (bias 접기 전) | corr | 최저 |
|---|---:|---:|
| 규칙 레시피, Q/K/V 까지 per-channel | 0.9773 | 0.9706 |
| 규칙 레시피, Q/K/V per-tensor | 0.9773 | 0.9696 |

정확도 차이가 없어 이 제약의 비용은 없다.

## 5. 배포 모델과 NPU

배포 단계는 이전과 같다(`fold_bias_into_k.py` Q/K/V, `fold_shape_consts.py`, 활성값 zero-point 를 받는 일반
bias 접기 복사본, `head_split.py --k`, `hoist_kfold_pad.py`). bias 접기 36 개, head split 24 + K 12, pad 끌어올림
36 개로 이전과 같다. ORT 비교 모델은 attn_out·FC2 출력에 int16 가짜 양자화를 넣은 것이다.

| | ORT | NPU | NPU − ORT |
|---|---:|---:|---:|
| 이전 (GELU 비대칭) | 0.9697 | 0.9690 (최저 0.9624) | −0.0007 (−1.9 SE) |
| **규칙 레시피** | 0.9785 | **0.9773** (최저 0.9683) | −0.0012 (−5.9 SE) |

NPU 에서 이전 대비 +0.0083, 64/64 문장 개선. 컴파일은 오류·메모리 초과 없이 됐다.

## 6. NPU − ORT 가 커진 이유

§6 은 GELU 하한 규칙(§8)을 넣기 전의 규칙 레시피에서 잰 것이다.

**결론.** 규칙 레시피에만 더 있는 간극(약 −0.0005)은 **NPU softmax ukernel 이 큰 확률을 체계적으로 작게 내는
오차**에 이 레시피가 더 민감해서 생긴다. 두 레시피에 공통으로 남는 약 −0.0007 ~ −0.0009 는 원인을 찾지 못했다.

### 6.1 어디서 처음 달라지나 — 잘라서 NPU 와 ORT 의 int8 값 비교 (16 문장)

배포 모델과 ORT 비교 모델을 같은 Q 출력에서 잘라(`onnx.utils.extract_model`) 각각 컴파일·실행했다. 여러 지점을
한 모델의 출력으로 꺼내면 CPU/NPU 배치가 충돌해 컴파일되지 않아 지점마다 따로 잘랐다. 상대 오차 =
rms(NPU − ORT) / rms(ORT), int8 단위.

| 지점 | 규칙: 일치 / 상대 오차 | 이전: 일치 / 상대 오차 |
|---|---|---|
| 층 0 embedding LN 출력 | 100 % / 0 | 100 % / 0 |
| 층 0 softmax 출력 | 93.3 % / 0.033 | 93.4 % / 0.033 |
| 층 0 context (attn_out 입력) | 78.3 % / 0.036 | 79.3 % / 0.035 |
| 층 0 attention 뒤 LN 출력 (a0) | 77.5 % / 0.023 | 88.5 % / 0.030 |
| 층 0 GELU 출력 | 93.0 % / 0.014 | 93.9 % / 0.005 |
| 층 0 FFN 뒤 LN 출력 | 48.8 % / 0.028 | 67.6 % / 0.039 |
| 층 5 GELU / FFN 뒤 LN | 85.4 % / 0.020, 16.2 % / 0.140 | 86.6 % / 0.008, 21.2 % / 0.180 |
| 층 10 GELU / FFN 뒤 LN | 90.6 % / 0.007, 17.5 % / 0.202 | 90.1 % / 0.005, 21.1 % / 0.245 |

차이는 층 0 의 softmax 에서 처음 생기고, 그 크기는 두 레시피가 같다.

### 6.2 국소 확인 — NPU 의 입력을 ORT 부분 모델에 넣기

| 확인 | 규칙 | 이전 |
|---|---:|---:|
| FC1 디스패치: NPU a0 → ORT(a0 → GELU 출력) vs NPU GELU 출력 | 100 % 일치 | 100 % 일치 |
| NPU softmax 출력·embedding LN 출력 → ORT(→ a0) vs NPU a0 | 97.6 % (ORT 그대로 77.5 %) | 98.7 % (88.5 %) |

FC1 디스패치는 정확하고, a0 차이의 대부분은 softmax 에서 온다. 남는 1 ~ 2.5 % 는 LN 쪽 작은 차이다.

### 6.3 softmax 오차의 모양 (층 0, 실제 토큰)

| ORT 값 (확률 ≈ 값 × 0.0077) | 원소 수 | NPU − ORT 평균 |
|---|---:|---:|
| 0 ~ 15 | 35,438 | +0.003 |
| 16 ~ 31 | 1,066 | −0.26 |
| 32 ~ 47 | 493 | −0.75 |
| 48 ~ 63 | 292 | −1.47 |
| 64 ~ 95 | 330 | −1.79 |
| 96 ~ 127 | 133 | −1.46 |

ORT 값 56 이상에서는 NPU 가 99 % 이상 낮다. 큰 attention 가중치가 1 ~ 2 % 작게 나온다.

softmax 디스패치는 NPU 에서 돈다(`--iree-amdaie-enable-ukernels=softmax`, 덤프에서 `softmax_12x32x32xf32` 가
amd-aie 타깃). ukernel(`softmax.cc`)은 exp2 결과, 1/sum, 확률, 출력 직전 값(`p · 1/s_out + 0.5`)을 모두 bf16 으로
좁히고, aie2p 의 bf16 변환은 −∞ 쪽으로 내림한다. 출력 직전 값은 LSB 단위라 [32, 64) 에서 bf16 간격이 0.25,
[64, 128) 에서 0.5 다. 이 경로를 numpy 로 흉내 내면(exp2·역수는 정확하다고 가정) 같은 방향의 치우침이 나오고 크기는
절반쯤이다(48 ~ 63: −0.51, 64 ~ 95: −0.77). 비트 단위 재현은 안 된다(약 90 % 일치) — 하드웨어 exp2·역수 명령의
근사는 재현하지 못했다.

### 6.4 이 오차가 간극에 미치는 영향 — ORT 의 모든 층 softmax 에 넣기 (64 문장)

6.3 의 값별 분포(8 단위 구간)에서 표본을 뽑아 ORT 의 12 층 softmax int8 출력에 더했다. 치우침이 없는 ORT 값 0 ~ 15
구간은 그대로 둔다(그 구간까지 독립 표본을 넣으면 실제보다 무작위 오차가 커져 ORT 가 NPU 보다 나빠진다).

| | ORT | ORT + softmax 오차 | NPU | NPU − ORT → NPU − (ORT + 오차) |
|---|---:|---:|---:|---|
| 규칙 레시피 | 0.9785 | **0.9779** | 0.9773 | −0.0012 → −0.0007 |
| 이전 레시피 | 0.9697 | 0.9699 | 0.9690 | −0.0007 → −0.0009 |

같은 softmax 오차에 규칙 레시피만 −0.0006 반응한다. 이것을 넣으면 두 레시피의 남은 간극이 비슷해진다.

### 6.5 원인이 아니었던 것

| 후보 | 확인 | 결과 |
|---|---|---|
| residual 채널별 정수 배수(②). α 가 커지면 LN 쪽 s 의 퍼짐이 커진다 | `computeResidualMultipliers` 를 파이썬으로 옮겨 24 지점 계산 | s 퍼짐 중앙 8.1 → 14.4 배. 배수 상대 오차는 두 모델 모두 0.001 % 이하, 공통 step 도 같다 |
| residual 합의 int16 step | ORT 의 residual 합(LN 입력)에 같은 step 의 가짜 양자화 | a0 일치 77.48 → 77.51 %, 간극 그대로 |
| LayerNorm ukernel 의 γ/β bf16 접기 | 컴파일러와 같은 식 `bf16(v / s_out) · s_out` | ORT 규칙 −0.0003, 이전 −0.0002. a0 일치는 오히려 내려감. softmax 오차와 같이 넣어도 남은 간극이 줄지 않음 |
| 이상값 채널 308 (규칙 레시피에서 s 가 평균의 10.9 배, 이전 5.8 배) | NPU a0 에서 채널 308 만 ORT 값으로 바꾸거나 그 반대 | 결과 차이 없음 |

### 6.6 고치는 방향 (하지 않음)

softmax ukernel 을 LayerNorm ukernel(work log §5.4, `769e9f74`)처럼 bf16 으로 좁히는 단계 없이 f32 lane 으로
계산하면 이 치우침이 줄 것으로 본다. 효과는 고쳐서 NPU 로 재야 한다.

## 7. 남은 오차가 어디 있나 — 연산별 leave-one-out (ORT, 64 문장)

규칙 레시피의 ORT 비교 모델(0.9785)에서 한 종류의 활성값 Q/DQ 만 빼서(fp32 로 되돌려) corr 이 얼마나 오르는지
봤다. 가중치는 DQ 를 fp32 상수로 바꿨다. int16 은 attn_out·FC2 출력의 int16 가짜 양자화를 뺀 것이다.

| int8 → fp32 로 되돌린 곳 (12 층) | corr | 최저 | 상승 |
|---|---:|---:|---:|
| (없음) | 0.9785 | 0.9722 | |

## 8. GELU 하한 규칙

**규칙.** 양자화된 활성값을 쓰는 곳이 GELU 하나뿐이면, 하한을 GELU 포화점 −C 로 올리고 상한(127·scale)은
그대로 둔 채 비대칭으로 다시 잡는다.

```
scale' = (127·scale + C) / 255,   zp = round(−128 + C / scale')
```

- "GELU 하나뿐" 은 구조로 판단한다. ONNX 에서 GELU 는 `x · 0.5 · (1 + erf(x / √2))` 로 풀려 있으므로, DQ 출력의
  소비자가 `Div(x, √2) → Erf → Add(1) → Mul(x, ·)` 와 그 Mul 뿐인지 본다. 다른 소비자(예: residual)가 있으면
  자른 범위가 그쪽 값을 틀리게 하므로 적용하지 않는다.
- 이미 비대칭이거나(zp ≠ 0) 128·scale 이 C 를 넘지 않으면 건너뛴다.
- 평가 데이터도, 보정 데이터도 쓰지 않는다. C 는 연산의 성질이다. 같은 생각을 소비 연산별 포화점 표로 넓히면
  SiLU(하한), sigmoid·tanh(양쪽), ReLU(하한 0)에도 적용된다. ReLU 의 경우는 기존 양자화 도구들이 이미 쓰는 방식이다.
- BERT 에서는 FC1 출력 12 곳이 걸렸다. scale 0.52 ~ 0.67 배, zp −63 ~ −119.

**C 와 상한을 바꿔 본 결과** (ORT, 64 문장, "보정" 은 상한을 보정 90 문장의 양수 쪽 99.999 백분위로 줄인 것):

| 하한 | 상한 그대로 | 상한 보정 |
|---:|---|---|
| −3 | 0.9853 (최저 0.9784) | 0.9853 (0.9794) |
| **−4** | **0.9852 (0.9801)** | 0.9853 (0.9799) |
| −6 | 0.9851 (0.9807) | 0.9849 (0.9794) |
| −8 | 0.9850 (0.9808) | 0.9849 (0.9800) |

C 를 −3 ~ −8 로 바꿔도 거의 같아 문턱값에 둔감하다. 상한을 줄이는 것은 효과가 없어 규칙에 넣지 않았다.
FC1 출력을 아예 fp32 로 둔 경우(+0.0091) 중 +0.0067 을 찾는다.

**컴파일러.** 바꾸지 않았다. 출력 zero-point 는 `AMDAIEPerChannelIntegerRequantization` 이 이미 받고(`+ zp`),
GELU 입력 dequant 의 `− zp` 도 그대로 컴파일된다. 입력 쪽 비대칭(§1, GELU 출력)과 달리 matmul 의 출력이라
보정 항 c[n] 표가 필요 없다. 메모리는 늘지 않는다(원소는 그대로 int8, 층마다 상수 하나).

**NPU** (64 문장, ORT 비교 모델에도 같은 규칙):

| | ORT | NPU | NPU − ORT |
|---|---:|---:|---:|
| 규칙 레시피 | 0.9785 | 0.9773 (최저 0.9683) | −0.0012 (−5.9 SE) |
| **+ GELU 하한 규칙** | 0.9852 | **0.9845** (최저 0.9796) | −0.0007 (−4.8 SE) |

NPU 에서 +0.0072, 64/64 문장 개선. 컴파일은 오류 없이 됐다. NPU − ORT 가 줄어든 이유는 보지 않았다.
