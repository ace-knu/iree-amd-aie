# 2026-09-11 — K축 bias 접합(Method A): 음성. 컴파일러 패스로 갈 가치 없음

> ⚠️ **2026-09-11 오후 뒤집힘**: 아래 음성 판정은 1열 프로토타입의 한계였다. 2열 + K=800 정렬로
> 정확도 손실(16.5→0.5 LSB)과 디스패치 증가(+60→−12)가 둘 다 사라진다 —
> `docs/2026-09-11_k_axis_bias_fold_two_column_fix.md` 를 볼 것.

## 0. 결론

ONNX 레벨 프로토타입으로 끝까지 재봤다. **속도 이득이 없고(−0.8%, 노이즈 범위),
디스패치는 오히려 늘고(+60), 정확도는 −0.0115 깎인다.** 컴파일러 패스 구현을 권하지 않는다.

프로토타입을 먼저 만든 판단은 옳았다 — 패스를 다 만든 뒤에 알았을 결과다.

## 1. 무엇을 했나

`bert_base_int8.onnx` 의 **QKV matmul 36개**(레이어당 3개 × 12층)에 대해:

```
[기존]   MatMul(dq(x), dq(w)) -> Q(m) -> DQ(m) -> Add(bias) -> Reshape -> ... -> Q(a)
[재작성] x_aug = Concat(x_i8, c)                       (레이어당 1개, Q/K/V 공유)
         MatMul(dq(x_aug), dq(w_aug)) ------------------> Reshape -> ... -> Q(a)
         w_aug = [w_i8 ; b_i8],  b_i8[n] = round(bias[n] / (c · x_scale · w_scale))
```

`X·W + c·b_i8·x_scale·w_scale = X·W + bias` 이므로 **텐서가 2개로 유지**되고,
Method B 를 막았던 "3번째 채널 → packet-flow 강제 → hang" 이 발생하지 않는다.

`c` 는 레이어별 공유로 정했다 (개별 c 는 Q/K/V 가 `x_aug` 를 공유할 수 없어 증강 비용이
3배가 된다). 레이어별 c = {0:26, 1:30, 2:33, 3:27, 4:18, 5:18, 6:18, 7:25, 8:17, 9:16, 10:12, 11:5}.
zero point 가 전부 0 인 것을 확인하고 발동시켰다.

도구: `_local/int8_debug/tools/fold_bias_into_k.py` (999 → 915 노드),
통제군 `strip_qkv_qdq.py`, c 선택 분석 `bias_shared_c.py`.

## 2. 속도 — 이득 없음

| | 디스패치 | 3회 실행 시간 (교차 측정 3라운드) |
|---|---|---|
| 원본 | **329** | 24.1s / 23.8s / 23.9s |
| K접합 | **389** (+60) | 23.9s / 23.6s / 23.7s |

**차이 0.8%, 노이즈 범위.**

⚠️ 첫 측정에서 −23% 가 나왔는데 **경합 노이즈**였다(측정 시작 시 `NPU: BUSY`).
A/B 를 교차로 돌려야 한다 — 순차로 재면 호스트 부하 변동이 그대로 들어온다.

### 디스패치가 왜 늘었나

K 가 768 → **769** 가 되면서 `AMDAIEPadContractionDispatches` 의 K 패딩(배수 32)이
발동한다. 768 은 이미 32의 배수라 패딩 디스패치가 없었는데, 769 는 **800 으로 패딩**되며
피연산자마다 패딩 디스패치가 생긴다. 여기에 레이어당 `Concat` 1개가 더해지고,
제거된 `Q(m)/DQ(m)/Add`(이미 융합되어 matmul 당 약 1 디스패치)보다 많다.

즉 **"공짜 패딩 레인에 bias 를 넣는다"는 아이디어의 전제가 이 형상에서는 성립하지 않는다** —
K=768 은 이미 정렬되어 있어서 남는 레인이 없다.

## 3. 정확도 — 오히려 손해

torch 정답 대비, 전부 CPU/ORT:

| 모델 | corr | maxdiff |
|---|---|---|
| 원본 QDQ | 0.883656 | 3.468 |
| **통제군** — QKV 중간 반올림만 제거, bias 는 f32 | **0.921592** | — |
| **K접합** — 위 + bias 를 int8 로 K축에 접음 | **0.910111** | 3.223 |

**K접합의 순이득 +0.026 은 전부 "중간 int8 반올림 제거" 에서 오고,
bias 를 int8 로 만드는 것 자체는 −0.0115 를 도로 내놓는다.**

### 앞선 "묻힘" 판정의 정정

`bias_k_feasibility.py` 로 각 matmul 자기 출력 LSB 기준 오차를 재서 36/36 "묻힘"
(최대 0.097 LSB, 레이어별 공유 c 로는 0.153 LSB)이라고 판정했다. **국소적으로는 맞지만
e2e 로 과대 해석한 것이었다.** 이 모델은 `docs/2026-09-10_bert_e2e_int8_vectorized.md` §5 에서
확인한 대로 **1 LSB flip 하나가 7% 출력 오차로 번지는 knife-edge** 이므로,
0.15 LSB 오차도 하류 반올림 경계를 넘겨 증폭된다.

**교훈: 국소 LSB 기준 판정을 e2e 정확도 판정으로 쓰면 안 된다. 통제군을 두고 e2e 로 재라.**

## 4. 그래서 무엇을 할 것인가

- **K축 bias 접합은 접는다.** 속도 이득 0, 정확도 손해, 디스패치 증가.
- **"중간 재양자화 제거" 는 따로 챙길 가치가 있다** — bias 와 무관하게 얻어지고
  (QKV 36개만 해도 corr 0.884 → 0.922), K접합보다 오히려 좋다.
  구현은 양자화 형식을 바꾸거나(`MatMulInteger` 계열) 생성 후 Q/DQ 쌍을 제거하면 된다.
- **정확도 최대 레버는 여전히 per-channel**(0.884 → 0.968)이고, 그건 NPU 백엔드가
  컴파일하지 못하는 상태다 — `docs/2026-09-10_per_channel_int8_blocked_in_npu_backend.md`.
  조사는 끝나 있고 구현만 남았다.
- Method B(accumulator 접합)도 여전히 막혀 있다(hang). bias 융합 자체를 당분간 보류해도
  잃는 게 없다는 것이 이번 결과의 의미다.

## 5. 재측정 — NPU 가 실제로 free 일 때, 그리고 더 나은 계측기로 (같은 날 오후)

§2 의 타이밍이 `NPU: BUSY` 경합에 오염됐을 가능성을 짚어 **NPU free 상태에서 다시 쟀다.**
그 과정에서 계측 방법 자체의 결함도 하나 찾았다.

### 5.1 계측기 교체: `iree-run-module` 벽시계 → `iree-benchmark-module`

`iree-run-module` 의 벽시계 24s 중 **실제 실행은 8.7s 뿐이고 ~15s(64%)는 190MB vmfb
로드 등 호스트 기동 오버헤드**였다. 즉 §2 는 신호를 3배 가까이 희석한 채로 재고 있었다.
`iree-benchmark-module` 은 모듈을 한 번 로드하고 invoke 만 반복하므로 이 오버헤드가 빠진다
(CV 약 1.6%).

### 5.2 교차 12라운드, 라운드마다 순서 반전 (AB/BA)

`--benchmark_repetitions=3`, 라운드 1·3·5…는 A→B, 2·4·6…은 B→A 로 호스트 드리프트를 상쇄.
전 구간 `with-npu-lock.sh` 로 락을 잡은 채 진행, 시작·중간 모두 `NPU: free` 확인.

| | 원본 (A) | K접합 (B) |
|---|---|---|
| 12라운드 평균 | **8981 ms** | **8936 ms** |

쌍체 차이 (B−A) = **−44.6 ms (−0.50%)**, sd 251 ms, **t = −0.62 (df=11), 95% CI
[−2.27%, +1.28%]**. **0 과 구분되지 않는다.**

(1차 6라운드만으로는 +1.08% 느림, CI [−0.55%, +2.70%] 이었다. 표본을 12로 늘리자 부호가
뒤집히고 CI 가 0 을 가운데 둔다 — 이것 자체가 "차이 없음"의 증거다.)

라운드별 B−A (ms): `85, 241, 155, −165, 120, 139, −468, −118, −558, −100, 43, 91`

곁가지: 호스트 CPU 시간은 B 가 일관되게 낮다(A ≈ 365 ms, B ≈ 337 ms). `Q(m)/DQ(m)/Add`
노드가 사라진 만큼 호스트측 일이 줄었는데, **디바이스 시간에는 전혀 반영되지 않는다.**

### 5.3 나머지 두 근거는 애초에 NPU 경합과 무관했다

- **디스패치 +60**: 정적 값이다. `iree-dump-module | grep -c hal.command_buffer.dispatch`
  로 재확인 — 원본 **329**, K접합 **389**. 실행 조건과 무관.
- **정확도 −0.0115**: 전부 CPU/ORT 측정이라 NPU 를 쓰지도 않았다.

### 5.4 결론 (변경 없음)

**§0 의 판정 유지.** NPU 가 free 인 상태에서, 오버헤드를 걷어낸 계측기로, 12라운드 교차
측정해도 **속도 이득은 0**이다. 경합 노이즈가 이득을 가리고 있었던 게 아니다.
K축 bias 접합은 접는다.
